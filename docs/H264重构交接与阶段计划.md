## 1. 决策摘要（TL;DR）

- **方向**：在现有成像→传输链路里加一条 **ESP32-P4 硬件 H.264 编码支路**（`/dev/video11` V4L2 M2M），把 JCLINK 从"传整帧"改成"传码流"。
- **为什么**：本项目的唯一硬伤是传输带宽 —— USB raw 天花板 **1.39MB/s（≈2.3fps）**、JPEG **~292KB/s（≈8~11fps）**
  （[`HANDOVER.md:202`](../jc_p4_app/docs/HANDOVER.md#L202)）。H.264 @1Mbps = **125KB/s**，帧长 ~5KB，
  带宽减半的同时帧率翻 2~3 倍，且不再触发"大帧超 500ms 预算被丢"的策略。
- **成本**：`esp_h264` v1.0.4 已在依赖树（esp_video 的私有依赖），**不需要新增组件**；
  唯一开关 `CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE` 当前是关的
  （[`jc_p4_app/sdkconfig:2973`](../jc_p4_app/sdkconfig#L2973)）。
- **形态**：推荐 **形态②（ISP 直接出 YUV420 喂硬编；AI 支路只做送检帧的格式转换）**，理由见 §3.2。
- **交付路径**：先走 **板端编码 → JCLINK 0x07 → Qt 上位机 openh264 解码**（复用现有 90% 设施），
  M4 再评估板端 RTSP 或真 UVC gadget。
- **别做的事**：NuttX / Linux on P4（官方要求 chip rev **v3.0+**，本板 **rev v1.3**
  [`HANDOVER.md:675`](../jc_p4_app/docs/HANDOVER.md#L675)）；MicroPython P4（仍 preliminary）。
- **兜底 Plan B**（0.5 天、零风险）：若硬编在本板实在不可用，用 **PPA 把预览缩到 320×240 再硬件 JPEG**，
  单帧 ~8KB，现有 USB 链路即可 30fps。

## 3. 框架规划

### 3.1 现状模块 → 目标分层（重构映射）

```
采集层   app_camera(SC2336→ISP, 钉 CPU1, sensor 写信箱)   ← 唯一格式分歧点
处理层   app_imgpipe(帧池/双缓冲最新帧/AE采样/DN/运动估计) + app_camauto(AE/AWB/夜视)
识别层   app_faceai(esp-dl 检测+特征+1:N, K帧确认, 名单)
编码层   app_stream(硬件 JPEG → 0x05)                    ← 新增并列：app_h264(硬件 H.264 → 0x07)
传输层   app_usb_link(JCLINK/CDC + 帧解析 + cmd 回调) / app_netlink(TCP server)  两者同格式
UI 层    app_display(DSI+GT911+LVGL9 状态页)  其余 app_{i2c,wifi,eth,ble,audio,sdcard,rs485,battery,status}
PC 层    pc_host(protocol.py 库 / board_hub / jc_test / 回归脚本) · qt_host(C++/Qt6, jclink+image_frame+video_view)
```

重构目标（**最小侵入**，不推翻既有分层）：

1. 新增 **`main/app_h264enc.c/h`** —— 只管"YUV420 帧进 → H.264 NAL 出"，对外 `app_h264enc_open(fmt)/push(frame)/read_packet(cb)/set(bitrate,qp,i_period)`；不碰传输。
2. **`app_stream` 变成"编码器选择器"**：`fmt=jpeg|h264|raw` 三路共用同一个取帧/预算/统计骨架；0x05 保持向后兼容（JPEG/raw），新增 **0x07** 专载 H.264 访问单元。
3. **`app_camera` 的格式断言解耦**：把 [`app_camera.c:702`](../jc_p4_app/main/app_camera.c#L702) 的"必须 RGB565"改成"按 `s_cam.fourcc` 分派"，并让 ISP 输出格式成为**运行时/编译期可选**（`APP_CAM_OUT_FMT`）。
4. **AI 支路与编码支路解耦**：`app_imgpipe` 的帧池按格式打标签，AI 侧自己保证拿到它要的格式（转换成本只落在"送检帧"上）。
5. 成像统计（AE/AWB/亮度直方图）从 RGB565 迁到 **YUV 的 Y 平面**（Y 即灰度，计算量更小、精度足够）；夜视阶梯/DN 沿用。

### 3.2 数据通路三形态（选型）

```
①纯验证(M0)     CSI → ISP(YUV420) → /dev/video11 → 0x07 → USB/TCP → PC 落盘 ffplay
                （LVGL 显示与 esp-dl 全关，只为取数字）
②编码优先 ★推荐 CSI → ISP(YUV420) ─┬→ 硬编 → 0x07/RTSP
                                    └→ 送检帧 YUV420→RGB(PPA缩放/裁剪) → esp-dl
                                    AE/AWB 走 Y 平面；JPEG 预览作为 fallback 保留
③AI 优先        CSI → ISP(RGB565) ─┬→ esp-dl + JPEG(现状)
                                    └→ CPU RGB565→YUV420(460KB/帧) → 硬编
```

**选 ② 的理由**：同一时刻 ISP 只能出一个格式（§2.3 的 :702 断言就是这件事），③ 要为每帧付一次 30 万像素色彩转换 + 多一次 460KB 拷贝，是给 PSRAM 带宽加税；② 让硬件出 YUV、编码零转换，转换只发生在**被节流的送检帧**上（esp-dl 检测前本来就要重打包/缩放，见 [`app_faceai.cpp:1231-1237`](../jc_p4_app/main/app_faceai.cpp#L1231)）。
**风险**：② 需要迁 AE/AWB 到 Y 平面（动 `app_camauto`/`app_imgpipe`）——若 M0 证明 ISP 出不了 YUV420，则自动降级为 ③，再不行走 Plan B（PPA 缩放 + JPEG）。

### 3.3 协议扩展提案（JCLINK v1 → 增 0x07）

沿用帧结构 `'J''C' | type | seq | len(u32LE) | payload | crc16(CCITT-FALSE)`，`MAX_PAYLOAD` 不动（1MB，[protocol.py:26](../pc_host/protocol.py#L26)）。

```
0x07 载荷（全小端）:
  u8  codec      = 1 (H264 baseline)
  u8  flags      = bit0 keyframe(IDR) | bit1 has_sps_pps | bit2 last_frag
  u16 stream_id             ; 每次 stream on 自增，用于识别"新一轮码流"
  u32 pts_us                ; 采集时间戳（板端 monotonic）
  u32 frame_seq             ; 码流内帧号（用于上位机算丢帧/抖动）
  u16 width, u16 height
  u32 nal_len ; 随后 nal_len 字节 = 一个访问单元（SPS+PPS+IDR 或 P-frame）
```

设计要点：① 单帧 <20KB，**不会撞 500ms 大帧预算**；② SPS/PPS 随每个 IDR 携带 ⇒ 上位机随时起播；
③ 运行时参数命令扩到现有 `{"cmd":"stream", ...}`：加 `fmt=h264&bitrate=1000000&qp_min/qp_max=i_period=`，
并遵守既有纪律"**开始流恒带 fmt/fps/quality**"（[commit a8ace24]）；④ `link` 查询的 `tx_frames/tx_kb` 统计继续复用，用于 A/B 量测。

### 3.4 上位机改造点（`qt_host/`）

- 新增 `src/h264_decoder.cpp`：链 **openh264**（BSD，无解码器全家桶负担；baseline profile 够用）→ YUV420 → RGB888 → `QImage` → 现有 `video_view.cpp`。
- `image_frame.cpp` 增加 0x07 分支（解析上表头），保持 JPEG/raw 分支不变；`main_window.cpp` 角标显示 `h264 <bitrate>`。
- `--selftest` 扩一项：收 100 帧 → 断言解码成功率/首 IDR 等待时间，写进 `qt_host/README.md` 实测表。
- 备选（更省事但更重）：FFmpeg libavcodec；或 M4 阶段板端起 RTSP，让 VLC/浏览器播、上位机零改动。

## 5. 预算表（M1 前必须先按这张表自查，数字来自 §2.2/§2.3）

| 项 | 估算 | 说明 |
|---|---|---|
| DSI 连续刷新 | 800×1280×2B×60Hz ≈ **123MB/s**（估算，**M1 必测**） | 若实际按需刷新/降帧，这一项是最大变量 |
| 相机 RAW10 640×480@50 | **≈19MB/s**（本机实测口径） | 编码路线可把相机降到 25fps 省一半 |
| ISP 写 YUV420 @25fps | 460KB×25 ≈ **11.5MB/s** | 形态②新增 |
| 硬编读 YUV420 @25fps | ≈**11.5MB/s** | 硬件 DMA 读，与上同量级 |
| 0x07 出流 @1Mbps | **125KB/s** | 远低于 USB/TCP 天花板 |
| H.264 编码器内部内存 | 1080p ~140KB（**PSRAM**）；640×480 更低 | esp_h264 README |
| **内部 RAM 余量** | **<3.5KB** | ⚠️ 任何 `DRAM_ATTR` 新增都要先量这个；缓冲一律 PSRAM + cache/64B 对齐 |

| 项 | 实测 | 判定 |

### 两条被现实纠正的纪律（务必保留）

1. **改过 Kconfig 必须 `idf.py reconfigure`，只跑 `build` 会把组件侧新开的符号悄悄退回 `not set`**。
   现场：`CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE` 在一次"只 build"后变回 `# ... is not set`，
   于是 `esp_video_init.c:347` 的 `esp_video_create_h264_video_device()` 被编译掉 → `/dev/video11` 不存在（errno=2），
   现象极易被误判成"本板 rev v1.3 没有 H.264 编码器"。
2. **不要在 camera 任务（优先级 6，钉 CPU1）里做"忙等式发送"**：CDC 发送的 μs 级忙等会饿死 tinyUSB 任务（优先级 5），
   实测每帧白烧满 500ms 发送预算 → 相机从 50fps 掉到 **1.9fps**、`send_fail` 全量。
   ⇒ 编码留在 camera 回调里没问题（≈5ms），但 **任何外部慢速 I/O（CDC 发送、SD `fwrite`）都应交给低优先级任务**。
   注：本区 `app_h264enc.c:368` 的 `fwrite` 目前在 camera 回调内同步执行，SD 写入抖动需要盯。
3. 上位机侧：`protocol.Link.recv()` 默认 `want=(0x02,0x04)`，不显式带 `T_IMAGE` 时 0x05 帧会被解析后丢弃；
   烧录复位后 COM5(VID_303A:4001) 会短暂消失，采集脚本要"等端口出现"而不是写死端口。
4. 本机烧录口现为 **COM3**（CH340），JCLINK CDC 为 **COM5**；PowerShell 激活 IDF profile 后 `python` 会指向
   ESP 的 venv（要系统 Python 时别在激活后的会话里跑）。构建脚本 `_dev/build.ps1` 已做成工作区无关。
- 修复记录：[`docs/2026-10-22_storage挂载失败_删除注册失效_修复记录.md`](2026-10-22_storage挂载失败_删除注册失效_修复记录.md)（HW_H264 争内部 RAM → FAT 挂载失败 → 删除/注册 `not found`）

## 11. 本区 `app_h264enc` M0 实测（2026-10-23，COM3 + USB CDC，无 TF 卡）

> 路径：`app_camera` 把 `/dev/video0` 切到 YUV420 → `app_camera_set_frame_cb` 同步旁路 →
> `/dev/video11` M2M OUTPUT(USERPTR 零拷贝) → CAPTURE NAL → 队列 → sender_task →
> **JCLINK 0x07（USB CDC）** → `pc_host/h264_capture.py` 按 `stream_id` 落盘。
> 构建/运行：`_dev/build.ps1 -Task build`、`_dev/m0_link.ps1`（自动 flash + 同时抓 COM3/COM5）。
> 配置：`APP_CAM_OUT_FMT_YUV420=y`、`FEED_FPS=25`、`GOP=25`、`DUMP_SECONDS=8`、
> `EXP_LINES=100`、`WB_KR/KB=1450/1100`、`SINK_LINK=y`、`SINK_SD=n`；
> `IMG_PIPE/STREAM/FACEAI=n`；`HW_H264=y`（仅 sdkconfig，defaults 保持关闭）。

### 11.1 三个前置修正（都是本轮上板才暴露的）

| # | 问题 | 根因 | 修正 |
|---|---|---|---|
| 1 | `S_FMT(YUV420)` 返回 EINVAL，驱动无任何日志 | `G_FMT` 会 `memcpy` 整个 `stream->format`，而 `CAPTURE_VIDEO_SET_FORMAT` 只写 width/height/fourcc，**`type` 仍是 0**；拿回的结构体直接做 `S_FMT` → `esp_video_get_stream(0)` NULL → EINVAL | `S_FMT` 前显式重置 `fmt.type=VIDEO_CAPTURE`、width/height、`bytesperline=0`、`sizeimage=0`（app_camera.c） |
| 2 | 一半帧可能被丢 | YUV420 下 esp_video 可能不回填 `bytesused`（探针实测约一半为 0），而相机任务原先以 `bytesused > 0` 判有效 | YUV420 分支不再用 `bytesused` 判有效性，帧长按 `w*h*3/2` 自算（app_camera.c） |
| 3 | 画面过曝/偏色 | M0 关闭 FACEAI 后 app 级 AE/AWB 不运行：默认曝光 994 行过曝；固定 WB 用 AWB 偏置（1320/1645）会整体偏粉紫 | 固定 `gain=72` + 可调 `EXP_LINES`；新增 M0 专用 `WB_KR/WB_KB`；实测 `exp=100 / WB=1450/1100` 在当前逆光窗景下可看 |

> 另：`APP_H264_GOP` 默认改 25——该值同时被当 fps 传给编码器，必须与 `FEED_FPS` 一致。
> `sdkconfig.defaults` 里的 `HW_H264` 已注释（防生产重建又踩 `/storage` 挂载失败），M0 只在 sdkconfig 临时开。
> 慢 I/O 已全部移出 camera 回调：编码仍同步（≈5ms），SD 写卡/0x07 发送都在 `h264_tx`（prio 4, CPU0）。

### 11.2 最终数字（USB 0x07，零丢包）

| 阶段 | 目标 | 板端实测 | PC 实测 | 单帧均值 | 编码均值/峰值 | 帧数/IDR/错误 |
|---|---|---|---|---|---|---|
| 1 | 500 kbps, QP25-35 | 498 kbps | **500 kbps** | 2507 B | 4965 / 5146 µs | 199 / 8 / 0 |
| 2 | 1000 kbps, QP25-30 | 1002 kbps | **1007 kbps** | 5042 B | 4959 / 4987 µs | 199 / 8 / 0 |
| 3 | 2000 kbps, QP20-30 | 2072 kbps | **2080 kbps** | 10392 B | 4955 / 4992 µs | 200 / 8 / 0 |

- 编码 CPU 占空比：**12% of one core**（≈5 ms × 25 fps）
- 内部 RAM：注册时 free=219 KB；PSRAM free≈33 MB
- **USB 零丢包**：三份文件字节数与板端逐字节一致（498954 / 1003508 / 2078572）

  帧数 **199 / 199 / 200** 与板端一致，`ffmpeg -v warning` **零告警**
- ⚠️ 上位机读取端必须加大 RX 缓冲并**内存缓冲后再落盘**（`protocol.py` 已改 256KB +

### 11.3 画面颜色（M0 限制，不是布局问题）

- YUV 布局正确：把解码帧 U/V 交换后画面从粉变黄、仍不自然；中性 WB 下 U/V 均值回到
  ≈128 → 排除“ISP 布局 ≠ O_UYY_E_VYY”。
- 当前场景**逆着亮窗**，大面积高亮（解码 Y p50≈243）；M0 无 AE/AWB，靠固定
  `EXP_LINES/WB_KR/WB_KB` 无法同时兼顾窗和室内物体。颜色偏绿是固定 WB 的残余，
  **不是码流/布局错误**。
- 正确解法是 M1 把 AE/AWB 统计迁到 Y 平面后恢复闭环；届时再重测码率（当前码率

## 13. YUV420 自动曝光 + 人脸检测（2026-10-23）

### 13.1 架构

```
camera_task（YUV420 640x480，QBUF 前，三路帧回调）
  ├─ app_h264enc      零拷贝硬编（25fps 送编）
  ├─ app_camauto      8x8 稀疏采样真实 Y → AE 闭环（信箱写 exp/gain）
  └─ app_ai_detect    每 200ms 拷一帧 460KB 到 PSRAM staging
AI task（prio3/CPU0）: PPA YUV420→RGB565（12ms）→ esp-dl MSRMNP（17ms）
                       → 0x02 {faces,boxes,conv_ms,infer_ms,fps,drops}
```

- 检测只做**检测框**，不挂 `/storage`、不做识别/名单 → 不触发 HW_H264 + FAT 的 NO_MEM。
- 模块开关：`APP_AI_DETECT=y`、`APP_AI_DETECT_FPS=5`、`APP_AI_DETECT_SCORE=50`、
  `APP_AI_DETECT_CONVERT_PPA=y`；AE 沿用 `APP_CAM_AE*`，但 M2 下
  `APP_CAM_AE_FLICKER50` 默认关闭（见下）。
- 新的多路帧回调：`app_camera_add_frame_cb()`（3 槽，`set_frame_cb` 仍是槽 0）。

### 13.2 关键发现：ISP 的 YUV420 是 O_UYY_E_VYY 打包布局

`esp_video` 把 `V4L2_PIX_FMT_YUV420` 直接映射成硬编要的
`ESP_H264_RAW_FMT_O_UYY_E_VYY`（`esp_h264_types.h:49`）：

```
line 1: u y y u y y ...     (偶行 U)
line 2: v y y v y y ...     (奇行 V)
行字节数 = w*3/2，整帧仍是 w*h*3/2
```

- **不是平面 YU12**。按平面布局做 CPU 转换/PPA 配置会得到彩色噪声（已实测）；
  硬编不受影响，AE 的整帧均值也不受影响（因此之前没暴露）。
- 修正：
  - AE 只采样每行 `3n+1/3n+2` 的 Y 字节；
  - CPU 回退按打包布局取 `U(偶行)/V(奇行)` + 本行 Y；
  - **PPA 的 YUV420 输入正好就是这个打包布局**：首帧用打包布局做像素对照，
    实测 max channel delta = **0**，因此默认走 PPA（12ms/帧），CPU 仅作回退。
- `app_h264enc` 的 `y_plane_mean()` 也改成按打包布局采样，日志 Y 值现在是真实亮度。

### 13.3 实测（640×480，USB CDC，室内）

|---|---|
| AE 目标/收敛 | 目标 120；初始 exp100/gain72（Y≈148）→ 稳定 **exp≈328-340 / gain≈46-47 / Y=120-122**，无往复 |
| 编码 | 21-22fps（开检测前 24fps），enc≈5.0ms，avg≈4-6KB/帧（约 90-110KB/s），err=0 |

### 14.4 关键坑（本轮新增）

1. **FAT 注册 NO_MEM 真因是 VFS 槽位满**（不是堆不够）：`VFS_MAX_COUNT=16` 后挂载成功。
2. **SD 卡未插时挂载失败仍占用 FATFS 卷上下文**：关闭 SD 初始化后 `/storage` 才注册成功。
3. **boot 阶段 `app_usb_link_log` 会被 H.264 发送长期占住 tx_lock**：挂载/切源等 boot 路径不要走 USB 日志。
4. **DB 导出 16KB 分片突发会丢/坏块**：分片间隔 1 tick → **20ms**，备份稳定。
5. **`stream off` 停流路径不可用 → 改为常开推流**：关编码器后重开需要 46KB
   参考帧，faceai/imgpipe 起来后内部 RAM 放不下；且 off 的 ack 路径会触发
   newlib stdio 锁分配失败 abort（堆碎片化）。M2 固件现在 **`stream off` 只回
   ack（`msg=stream off ignored (always-on)`）、不停流**；识别回归也在推流中
   直接跑（25/25 通过）。真正停流留待内部 RAM 预算完成后再做。
6. **USB 发送预算按类型区分**：H.264(0x07) 50ms、控制/ack 500ms。视频拥塞时
   快速丢帧，避免占住 tx_lock 把 0x02 ack 饿死。
6. **相机被倒置摆放时人脸检测不出**：MSRMNP 不处理 180° 人脸；需把摄像头摆正
   （H.264 画面与送检帧同向）。
