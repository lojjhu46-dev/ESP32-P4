# 2026-10-22 修复记录：`/storage` 挂载失败导致名单「删除/注册」全部失效

> 一句话结论：**开 `CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE=y` 后，`esp_video_init()` 占满内部 RAM，
> faceai 任务挂 FAT `/storage` 时报 `ESP_ERR_NO_MEM`，`s_db_ok=false` → 删除/注册全部 `not found`，
> 而名单仍能从 NVS 兜底显示，界面看起来「删除点了没反应」。**

- 日期：2026-10-22
- 涉及工程：`D:\esp32project\ESP32-P4`（分支 `feature/usb-video-qt-host`）
- 涉及端：板端固件 `jc_p4_app` + 上位机 `qt_host`
- 触发方：未提交的 H.264 M0 配置改动（`sdkconfig` 2026-10-22 19:26）

---

## 1. 症状（用户视角）

1. 上位机「名单」页列出 `musk`(1 特征)、`personA`(3 特征)；
2. 选中 `personA` → 点「删除选中」→ 弹「删除 personA 的全部特征?」→ 点 **Yes**；
3. 列表刷新后 **`personA` 仍然在**，没有任何错误提示（错误只写在右下角日志区）。

用命令行直接复现（`pc_host/jc_test.py`，与上位机发的是同一条命令）：

```powershell
python pc_host\jc_test.py --serial COM5 delete personA
# <- {"event":"error","ack":"delete","msg":"not found", ...}
```

即：**板端认为「这个名字不存在」**，尽管 `list` 刚返回 `lib:["musk","personA"]`。

---

## 2. 根因链

```
sdkconfig: CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE=y
        │
        ▼
esp_video_init() 注册 H264 编解码设备，预留内部 RAM（与 camera/ISP、USB CDC ring 抢同一池）
        │
        ▼
faceai_task 启动（main.c 里排在 camera/stream 之后）挂 /storage(FAT+wear_levelling)
        │  esp_vfs_fat_spiflash_mount_rw_wl() → ESP_ERR_NO_MEM
        ▼
s_wl/s_db 未创建 → s_db_ok = false
        │
        ├─ delete 分支被 `if (s_db_ok)` 门控 → 一次都不删 → removed=0 → send_result("error","not found")
        ├─ register 分支 → send_result("error","feature db unavailable")
        └─ 名表走 NVS 兜底加载（names.json 读不到也写不进）→ 界面「名单还在」的假象
```

关键代码位置（`jc_p4_app/main/app_faceai.cpp`）：

| 位置 | 内容 |
|---|---|
| `:3066-3077` | `esp_vfs_fat_spiflash_mount_rw_wl(FACE_DB_MOUNT, FACE_DB_PART, ...)`，失败仅 `ESP_LOGW`，不阻止后续流程 |
| `:3080` | `names_load()`（names.json 优先，NVS 兜底） |
| `:2552-2577` | `delete` 分支：`int removed = 0; if (s_db_ok) { ... }`，`removed==0` 时统一回 `not found` |
| `:3013-3015` | `list`：置 `s_lib_dirty=true`，结果帧附带 `lib/lib_feats` |
| `:924-952` | `send_result()` 里把 `lib`（名字）与 `lib_feats`（每人特征条数）挂进结果帧 |

> ⚠️ 迷惑点：`lib` 来自内存名表 `s_names[]`，与 `face.db` 是否可用**无关**。
> 所以「名字列出来了」完全不能证明特征库是好的。

## 3. 证据

### 3.1 故障启动日志（CH340，`tools/serial_capture.ps1`）

```
I (1776) ble: pre-sched heap: internal free=132360 largest=90112
I (2219) sdcard: mount failed: ESP_ERR_TIMEOUT (no card inserted?)     ← 无关：SD 卡确实没插
E (8026) esp_video_sensor: ctrl id=2000a is not supported              ← camera/ISP 初始化进行中
W (8099) faceai: feature db mount failed: ESP_ERR_NO_MEM (detect only)
W (8056) faceai: names.json missing -> migrated 4 name(s) from NVS
W (8060) faceai: names.json write failed (fallback NVS only)
I (8237) faceai: models loaded in 171 ms
```

三个「W」连在一起就是完整证据：分区没挂上 → names.json 读不到 → 迁移自 NVS → 写回也失败。

### 3.2 对照实验（决定性）

仅把 `CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE` 改回 `is not set`，重编烧录（无需改任何 C 代码），日志变为：

```
I (8065) faceai: feature db partition 'storage' mounted at /storage (first boot formats it, ~few s)
I (8067) faceai: names loaded from /storage/names.json: 4
I (8246) faceai: feature db /storage/face.db: 4 feat(s) in lib, name table 4
I (8246) faceai: models loaded in 176 ms
```

时序上 `esp_video_sensor`（camera/ISP）在 8026~8400 之间与 `faceai_task` 的 mount（8099）**并发**，
内部 RAM 余量本来就在临界（`largest=90112`，且 H.264 通路和 USB CDC 都需要内部 DMA 可及内存），
H.264 一开即被推过阈值。

固件体积对照：`6,329,712 B`（开 H264）→ `6,306,768 B`（关 H264）。

## 4. 修复

| 文件 | 改动 |
|---|---|
| `jc_p4_app/sdkconfig` | `CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE=y` → `# CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE is not set` |
| `jc_p4_app/sdkconfig.defaults` | 同一项注释掉，并补 5 行说明（含本记录的核心结论），防止以后重建 sdkconfig 又踩回 |

操作序列：

```powershell
. C:\Espressif\tools\Microsoft.v5.5.5.PowerShell_profile.ps1
cd D:\esp32project\ESP32-P4\jc_p4_app
idf.py -p COM3 flash        # 会因 sdkconfig 变更自动 reconfigure；COM3=CH340
```

> 本次没有改任何 C 代码，也没有动 `esp_video` 组件：问题纯粹是 Kconfig 打开后内部 RAM 不够。

## 5. 验收

```powershell
# 删除
python pc_host\jc_test.py --serial COM5 delete personA
# <- {"event":"deleted","ack":"delete","msg":"deleted 3 feat(s) of personA","lib":["musk"],"lib_feats":[1]}

# 复位后复查（验证持久化，而不是只改了内存）
python jc_p4_app\tools\serial_capture.ps1 -PortName COM3 -Seconds 9
# I (8066) faceai: names loaded from /storage/names.json: 1
# I (8249) faceai: feature db /storage/face.db: 1 feat(s) in lib, name table 1
python pc_host\jc_test.py --serial COM5 list
# <- {"event":"list","lib":["musk"],"lib_feats":[1]}
```

验收口径：**删除后立即生效 + 复位后仍生效**（两条都满足才算修好，只看第一条会漏掉「只删了内存」的情况）。

## 6. 副作用与遗留

1. `personA` 的 3 条特征已被真正删除（是用户在界面上要求删的那条）。需要的话重新注册。
2. **H.264 M0 被阻塞**：只要开 `HW_H264`，`/storage` 就挂不上 → 识别/注册/删除全废。
   要推进 M0，必须先做内部 RAM 预算（可选方向，按性价比排序）：
   - 把 `faceai_task` 的 FAT 挂载**前移到 `app_camera_init()` 之前**（`main.c:130` 之前），先占住 FAT 常驻缓冲；
   - 给 mount 加「失败重试 + 明确错误上报」，避免静默降级；
   - 重新核算 ISP/CSI 的 DMA 缓冲、USB CDC ring（128KB PSRAM 已外置）、BLE 栈占用；
   - 接受「H264 与 AI/特征库不同时在线」的分时策略（M0 探针阶段可以不要 AI）。
3. 上位机侧无改动。它的删除流程本身是对的（`{"cmd":"delete","id":<name>}`，板端 `:2510-2514` 同时兼容 `id`/`name`）。

## 7. 建议的代码级改进（未实施，供后续排期）

| # | 建议 | 理由 |
|---|---|---|
| 1 | mount 失败时置一个显式状态，`delete`/`register` 回 `"feature db unavailable"` 而不是 `"not found"` | `not found` 把「库没开」伪装成「名字不存在」，本次排障 90% 时间浪费在这上面 |
| 2 | mount 失败时通过 0x04 日志帧（不只是本地 `ESP_LOGW`）推一条到 PC，上位机状态栏标红 | 用户默认看不到板端串口日志 |
| 3 | 启动自检：`s_db_ok == false` 时让「名单」页顶部显示横幅 | 名单显示 ≠ 库可用，必须在 UI 上说清 |
| 4 | `idf.py size-components` 加入 H264 验证清单（本次实测 `libespressif__esp_h264.a` 静态 DRAM 占用为 0，问题全在运行期） | 静态占用会误判，必须看运行期 heap |
