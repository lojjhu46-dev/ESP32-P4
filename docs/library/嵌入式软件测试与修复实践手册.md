## 3. A 章 · 板级 bring-up 与传输链路

### A1（深度）USB 视频流半年跑不起来：一个返回值误用 + 一个 tick 粒度

- **现象**：JCLINK over TCP 一切正常；换到 USB CDC 后 0x05 图像帧"发不出去"，JPEG 只有 ~79KB/s、raw 大帧直接缺失。当时所有怀疑都指向"USB 枚举/带宽/主机端"。
- **取证**：`_usb_bench.py` 测到板端 `tx` 计数在增长但主机收不满；把 `write_queue` 的返回原样打印，发现"成功"时也返回非 0。
- **根因**（两处叠加，改动前必读）：
  1. `tinyusb_cdcacm_write_queue()` 返回 **`size_t` 已入队字节数**，旧代码当 `esp_err_t` 用：`esp_err_t err = ...; if (err != ESP_OK) return err;` ⇒ **每一次发送都被判为失败**。TCP 走另一个后端，所以大半年没暴露。
  2. FIFO 满时用 `vTaskDelay(1)` 等排水（1 tick 粒度太粗），吞吐被死死钉在 **~170KB/s**。
- **修复**：`jc_p4_app/main/app_usb_link.c` —— 按字节数循环推进；忙等改 `esp_rom_delay_us(50)` × 最多 64 次后才让出 1 tick（代码里留着这段实测注释）。
- **验收**：JPEG **79 → 283KB/s**（≈8~11fps），raw **完整 1.39MB/s（±0.5%，≈2.3fps）**，零丢包；同固件回归 25/25。USB 协商速率 `HIGH (480Mbps)` ⇒ 1.4MB/s 不是总线限制，是 CDC 路径限制。
- **教训**：① "另一条链路正常"能排除一大半嫌疑，但排除不了共用协议栈里的分支；② 判断吞吐不要看平均，看**单次 write 的返回语义**；③ 单位/粒度类 bug（tick vs μs）只能靠数量级异常识别——170KB/s 这个数一出现就该去查 tick。

- **被推翻的假设**
  | 假设 | 当时的理由 | 为什么错 |
  |---|---|---|
  | USB 带宽不够 / 主机端驱动问题 | 只有 USB 慢，TCP 快 | 两条链路只差后端，板端发送逻辑早已失败 |
  | FIFO 开小了，放大就好 | 直觉 | 见 A2：越大反而越慢 |
  | 大帧被截断是 MTU/分包问题 | raw 614KB 发不出 | 是发送预算与 FIFO 排空粒度 |

### A2 CDC FIFO 放大：越大越慢，4096 起开不了机

- **现象**：想靠加大 `CONFIG_TINYUSB_CDC_TX_BUFSIZE` 提速。
- **取证**（同场扫描，`_usb_bench.py`）：

  | TX FIFO | JPEG@20fps | raw@10fps | 能否启动 |
  |---|---|---|---|
  | **512（选定）** | **292 KB/s** | **1390 KB/s** | ✅ |
  | 1024 (+0.5KB) | 211 KB/s | 1113 KB/s | ✅ |
  | 2048 (+1.5KB) | 245 KB/s | 840 KB/s | ✅ |
  | 4096 (+3.5KB) | — | — | ❌ `assert failed: vApplicationGetIdleTaskMemory` |
  | 8192 (+7.7KB) | — | — | ❌ `assert failed: esp_startup_start_app (res == pdTRUE)` |

- **根因**：FIFO 变大后单次排空时间变长、突发更多，效率反降；且本板内部 RAM 余量 **< 3.5KB**，几 KB 就足以压垮启动窗口。**搬到 PSRAM 也不行**：`SOC_DMA_LOW/HIGH = 0x4ff00000..0x4ffc0000` 只覆盖内部 DRAM，esp_tinyusb 自己注释写明 "USB DMA buffers live in internal SRAM" 并强制 `DRAM_ATTR`。
- **修复**：定 512；把"raw 连续推流"改成 **JPEG 预览 + raw 按需单帧抓取**（单帧 ~0.5s），颜色标定/取证够用。
- **验收**：`qt_host.exe --selftest --serial COM5 --grab-raw out.png` → `grab-raw: ok=1 640x480 data=614400B`。
- **教训**（判据 P6）：本板任何"加几 KB 内存"的改动都要先问"启动窗口还剩多少"，而不是"堆还剩多少"。

### A3 `stream off` 不敢真停流：重开需要 46KB 参考帧

- **现象**：M2 期间 `stream off` 后 `stream on`，0x07 码流不再出现（`s_h.enabled=false`）。
- **根因**（两条，都在 `docs/library/H264重构交接与阶段计划.md` §14.4）：关闭编码器后再开需要 **46KB 内部 RAM** 放参考帧，faceai/imgpipe 起来后放不下；且 off 的 ack 路径会触发 newlib stdio 锁分配失败而 abort（堆碎片化）。
- **修复**：M2 固件 `stream off` **只回 ack 不停流**（`msg=stream off ignored (always-on)`），识别回归也在推流中直接跑（25/25）。真正停流留待内部 RAM 预算完成后再做。
- **教训**：与其"修好停流"，不如先证明"不停流也能验收"；把不可靠的路径显式降级并留下可检索的 msg 文案，比留一个偶发死机强。

### A4 热改 H.264 码率/QP 直接把编码器打死

- **现象**：识别 + 推流时在 Qt 里改码率/QP，画面立刻 0fps，只能复位板子恢复。
- **根因**：下发编码参数会 `enc_close/enc_open`，此刻内部 RAM 最大块不足以重新分配参考帧 → 重开失败。
- **修复**：Qt 加二次确认与提示；纪律是**要改画质就改固件默认值（Kconfig/sdkconfig）后重刷，不在运行期热改**。
- **教训**：判据 P6 的第三个受害者；"能改"和"敢在运行时改"是两件事。

### A5 吞吐测量的三个坑（不做对，读数全是错的）

1. **CDC 是背压式的**：主机不读 → 驱动缓冲满 → 板端 FIFO 满 → 0x05 超 500ms 预算被丢。测量期间必须**持续读**（`_usb_bench.py` 后台 Reader 线程），否则测的是"丢弃率"（只数到 0x02 小帧 ≈7KB/s）。
2. **不能用 PC 侧计数**：`usbser.sys` 突发交付 + 缓冲，按首末帧时间差算 fps/带宽抖动 **±29%**（同配置 786~1432 KB/s），还会因集中排放出现 **45fps 假读数**。口径一律用**板端 tx 计数 − 空闲基线**。
3. **不能在流中发查询**：流开着时 0x02 结果帧洪泛，`cmd_and_wait` 会取到普通结果帧（读数全废）。正确做法：关流 → 静默 → 查 `link` 取 `tx_frames/tx_kb`。

### A6 `S_FMT(YUV420)` 返回 EINVAL 且驱动零日志

- **现象**：M0 上板，`G_FMT` 拿回来的结构体直接 `S_FMT` → `EINVAL`，esp_video 什么都不打印。
- **根因**：`G_FMT` 会 `memcpy` 整个 `stream->format`，而 `CAPTURE_VIDEO_SET_FORMAT` 只写 width/height/fourcc，**`type` 仍是 0** → `esp_video_get_stream(0)` 返回 NULL。
- **修复**：`S_FMT` 前显式重置 `fmt.type=VIDEO_CAPTURE`、width/height、`bytesperline=0`、`sizeimage=0`（`app_camera.c`）。
- **教训**：驱动不报错 ≠ 驱动没错；把 ioctl 的输入结构体当作"未初始化内存"对待。

### A7 `bytesused` 在 YUV420 下一半是 0，导致一半帧被判无效

- **现象**：约一半帧被丢，无日志。
- **根因**：YUV420 下 esp_video 可能不回填 `bytesused`（探针实测约一半为 0），而相机任务用 `bytesused > 0` 判有效。
- **修复**：YUV420 分支不再用 `bytesused`，帧长按 `w*h*3/2` 自算。
- **教训**：V4L2 的"可选"字段在不同 fourcc 下行为不同，别当作契约。

### A8 `/storage` 挂载失败让删除/注册全部失效（详见 `docs/library/2026-10-22_storage挂载失败_删除注册失效_修复记录.md`）

- **现象**：名单里 `personA` 还在，点删除 → 列表刷新后仍在，无提示；`jc_test.py delete personA` 回 `{"event":"error","msg":"not found"}`。
- **根因**（链）：`CONFIG_ESP_VIDEO_ENABLE_HW_H264_VIDEO_DEVICE=y` → `esp_video_init()` 预留内部 RAM → `faceai_task` 挂 FAT+wear_levelling 时 `ESP_ERR_NO_MEM` → `s_db_ok=false` → delete/register 被 `if (s_db_ok)` 门控 → 名表走 NVS 兜底，界面"名单还在"。
- **修复**：关掉该 Kconfig（`sdkconfig` + `sdkconfig.defaults` 同步注释并写清来历）；本次**没改一行 C 代码**。
- **取证**（对照实验）：日志三连 `W feature db mount failed: ESP_ERR_NO_MEM` → `W names.json missing -> migrated 4 name(s) from NVS` → `W names.json write failed`；固件体积 `6,329,712 B → 6,306,768 B`。
- **验收**：关闭后启动日志变 `feature db partition 'storage' mounted at /storage` + `names loaded from /storage/names.json: 4` + `feature db /storage/face.db: 4 feat(s) in lib`；删除必须**立即生效 + 复位后仍生效**两条都过。
- **教训**：`not found` 把"库没开"伪装成"名字不存在"；错误码必须区分能力缺失与目标缺失（后续已补 `feature db unavailable` 路径与 0x04 日志帧转发）。

### A9 FATFS 长文件名默认关闭 → `names.json` 从未写成功；名表加载时机早于挂载

- **现象**：启动日志 `names.json missing -> migrated 12 name(s) from NVS` 紧跟 `names.json write failed (fallback NVS only)`。
- **根因**：`CONFIG_FATFS_LFN_NONE=y`，而 `json` 扩展名 **4 字符**（非 8.3 合法）→ `fopen`/`rename` 全失败；`names.tmp` 是合法 8.3，所以临时文件能建、改名失败。另一处：`names_load()` 原先在 `app_faceai_init()` 里调用，**早于** `faceai_task` 内的挂载 → 挂载前读 names.json 必然失败，"空名表"会覆盖真实名表。
- **修复**：`CONFIG_FATFS_LFN_HEAP=y` + `names_save_json` 增加"tmp+rename 失败则直写目标"的兜底；`names_load()` 移到 mount 之后。
- **验收**：真机 `names loaded from /storage/names.json: N`，且断电重启后条数不变。
- **教训**：在 FAT 分区新增任何"文件存储"类功能，必须先确认 LFN 配置并跑一次真机写入 + 复位复查；兜底机制会**掩盖**主路径失效（判据 P1 的又一形态）。

## 4. B 章 · 内存 · 启动窗口 · 构建

### B1（深度）BLE 一使能就无限重启：启动窗口的内部 RAM 贴零线

- **现象**：配置齐全、编译通过，烧录后板子在 `sleep_gpio` 后无限重启：`assert failed: vApplicationGetIdleTaskMemory port_common.c:53 (pxStackBufferTemp != NULL)`。
- **取证**（逐层收窄，这套顺序值得复用）：
  1. `BT=n` 构建正常启动 → 排除代码错误；
  2. 两版 `heap_init` 区域只差 **1.2KB** → 排除静态内存剧增；
  3. 在 `app_ble.c` 加 `__attribute__((constructor))` 探针（main 链接在最后，跑在 esp_hosted 构造器之后、调度器之前）：堆剩余 **142KB**、试分配 6KB OK、请求仅 **1536B** → 排除"请求病态"；
  4. 给本地 IDF `port_common.c` 断言前插打印 —— ⚠️ **此阶段 `printf` 会因 newlib 需要 malloc 而静默无输出，必须用 `esp_rom_printf`** → 拿到决定性的"空闲内部 RAM 已连续块碎片化"数据。
- **根因**：BT 栈在调度器启动前申请内部 RAM 连续块，而本板启动窗口内部 RAM 余量 < 3.5KB；idle 任务栈都分配不出来。不是请求大小问题，是**没有可合并的连续空闲块**。
- **修复**：压缩启动窗口占用（BLE 使能与相机/H264/大 FIFO 互斥），把可外置的缓冲搬 PSRAM，并把"CDC FIFO 512 + HW_H264 关闭 + 特定任务栈"作为已验证组合钉进 `sdkconfig.defaults` 注释。
- **验收**：`BT=y` 启动稳定，BLE 广播 "JC-P4"，`device address cc:8d:**:**:**:**`（来自 C6）。
- **教训**：① 判据 P6；② **启动早期打印要用 `esp_rom_printf`**；③ 堆统计"剩余总量"会骗人，要看**最大连续块**；④ 加 `constructor` 探针是获取"调度器前状态"的唯一实用手段。

### B2 IDF CMake 早期展开丢弃 `if(CONFIG)` 内的 `REQUIRES`（全工程性）

- **现象**：`app_ble.c: fatal error: nimble/nimble_port.h: No such file or directory`，且 `libbt.a` 未链接 —— 但 `app_ble.c` 明明在 SRCS 里。
- **根因**（读 `tools/cmake/component.cmake` + `scripts/component_get_requirements.cmake` 确认）：IDF 在**独立 CMake 脚本实例**里早期展开每个组件的 CMakeLists 收集 `REQUIRES`/`PRIV_REQUIRES`，**该实例里没有 CONFIG_\* 变量**；真实 configure 阶段传入的 REQUIRES 被静默丢弃（`__component_set_properties()` 不回填 `__REQUIRES`）。所以 `if(CONFIG_APP_ENABLE_BLE) list(APPEND requires bt esp_hosted) endif()` 从不生效，而 `list(APPEND srcs/include ...)` 走真实注册**有效** —— 这就是"源文件在编译列表里、依赖头目录/链接却缺失"的矛盾来源。
- **顺带澄清历史**：第十九节 WiFi 块里 `list(APPEND requires esp_wifi_remote esp_wifi)` 一直是死代码，wifi 能编译纯靠 `idf_component.yml` 托管依赖兜底；`bt` 不在 yml 里没兜底，故 BLE 首当其冲。
- **修复**：`main/CMakeLists.txt` 把 `esp_wifi_remote/esp_wifi/esp_hosted/bt` 全移进**无条件**的 `set(requires ...)`（组件在功能关闭时注册为空库，无副作用）；if 块只留 `srcs/includes`。
- **验收**：看 `build/project_description.json` 的 `build_component_info.main.reqs/priv_reqs` 是否包含目标组件——这是唯一可靠判据。
- **教训**：条件性依赖一律放进无条件基础列表；怀疑依赖关系时读 `project_description.json`，别猜 CMake 行为。

### B3 esp_hosted 新版 RPC 与出厂从机固件语义错配

- **现象**：`E ble: C6 bt controller init failed (check slave fw / SDIO)`。
- **根因**：`esp_hosted_bt_controller_init/enable` 走 feature-control RPC —— "controller 默认关闭、host 必须显式 init/enable" 是**新版从机**语义；出厂 2.3.x 的 BT controller **默认自启**（能力位图明确广播 `HCI over SDIO / BLE only`），只是不认识这条新 RPC。
- **修复**：init/enable 失败**降级为警告并继续**初始化 NimBLE，HCI 是否可用交给 sync 回调裁决 → 同一份代码新旧从机通吃。
- **教训**：能力位图先读，再决定"报错"还是"降级"；对上游语义差异要写成兼容分支而不是钉死版本。

### B4 WiFi 摘除的真凶是两层叠加（不是一次"版本不兼容"）

- **现象**：板载 ESP32-C6（SDIO slot1、复位 GPIO54 高有效）WiFi 一直起不来，先前结论是"等 C6 固件升级"，于是整个 WiFi 块被摘除。
- **根因**：① 组件版本错配：解析到 esp_hosted 3.0.7，与从机固件 2.3.2 "major version mismatch"；厂商 `wifi_scan` 模板的 `dependencies.lock` 给出配套对。② **TF 卡槽位错配**：`app_sdcard.c` 原来配 `SDMMC_HOST_SLOT_1`，但 TF 卡引脚（CLK43/CMD44/D0-3=39..42）实际是 P4 **SDMMC slot 0** → 与 esp_hosted 抢同一 SDMMC 主机 → **启动循环**。第 ② 层才是崩机真凶，第 ① 层只是连不上。
- **修复**：`esp_wifi_remote 0.14.2 + esp_hosted 2.12.13`（2.12.13 修了 RX 任务/队列初始化竞态）；`main/CMakeLists.txt` 用 `idf_component_get_property` 显式补 injected 垫片头目录（IDF 5.5.5 下 `esp_wifi.h not found`）；`sdkconfig.defaults` 加 esp_hosted 板级块 + **`CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192`**（默认 3584 被 `esp_wifi_init`+hosted 链打穿 → Stack protection fault）+ **`CONFIG_FREERTOS_HZ=1000`**（100Hz 会报 bus jitter）；`app_wifi.c` 加 `WIFI_STORAGE_FLASH`；新命令 `{"cmd":"wifi","ssid":"X","pass":"Y}` 运行时配网免重烧。
- **验收**：全链路真机通；BLE 广播 "JC-P4"。
- **教训**：① "两个现象一个结论"最危险 —— 连不上与起不来要分别归因；② 厂商 demo 的 `dependencies.lock` 是版本对的权威来源；③ 引脚表要对照 SoC 的 slot 分配，不靠"看起来是 slot 1"。

### B5 FAT 注册 NO_MEM 的真因是 VFS 槽位满 + SD 未插仍占卷上下文

- **现象**：`/storage` 挂载 `ESP_ERR_NO_MEM`，但堆明明够。
- **根因**：`CONFIG_VFS_MAX_COUNT` 默认 16 被占满；另：SD 卡未插时挂载失败**仍占用 FATFS 卷上下文**，导致 `/storage` 注册不进去。
- **修复**：`VFS_MAX_COUNT=16` 之后挂载成功；关闭 SD 初始化。
- **教训**（判据 P6 的第三种形态）：`NO_MEM` 不一定来自 malloc —— VFS/卷/描述符这类"固定数量表"耗尽也报同样的错。

### B6 boot 阶段发 USB 日志会把后续流程拖死

- **现象**：挂载/切源等 boot 路径调用 `app_usb_link_log()` 时行为异常。
- **根因**：boot 阶段 H.264 发送长期占住 `tx_lock`，日志帧等锁。
- **修复**：boot 路径不走 USB 日志，改本地 `ESP_LOG*`；运行期日志才用 0x04。
- **教训**：给"初始化期间"设计的可观测手段必须证明它不依赖尚未就绪的子系统。

### B7 构建失败却烧了旧固件（假 `exit 0`）

- **现象**：改了代码，"修复后行为完全没变"，一度怀疑固件没生效或板子有问题。
- **根因**：`int lost = 0;` 声明在 `goto out;` 之后 → C++ "jump to label crosses initialization" **编译失败**；脚本没透出真实退出码，随后照常执行 `flash`，把**上一版二进制**烧了进去。
- **修复**：变量声明上移到函数头；`_dev/build.ps1` 增加工作区断言 + 真实退出码透出 + 输出落文件。
- **教训**（判据 P16）：多副本工作区里，任何"构建/烧录"脚本都要回答三个问题——跑在哪个目录？退出码是真的吗？日志留在哪？

## 5. C 章 · 成像与算法在环

### C1（深度）同一张图两次结果不同：先证伪"算子有 bug"，再定位执行级硬件竞态

- **现象**：同图多次推理，特征相似度在 0.1~0.99 之间乱跳 → 人脸识别跨 boot 不可移植，阈值只能每次开机相对标定。
- **根因**（第一阶段，可修，2026-10-04）：**P4 双核 L1 互不一致 + `esp_cache_msync` 无跨核 IPI**。`jpeg_decoder_process` 的 invalidate 只作用于调用核；imgpipe 与 faceai 原先都没绑核，解码核 ≠ 读像素核时消费者核 L1 残留旧 cache 行；CAM 路径同样中招（`pipe_copy_into` 的 memcpy 在 CPU1 留脏行）。
  - **修复**：写侧 C2M 回写 + 读侧 M2C 失效（**按整槽 cap，不能按 `stride*height`**，任意高度下 size 未必 64B 对齐）+ imgpipe/faceai 钉 CPU0；诊断埋点常驻 `frm_crc/ai_crc/ai_crc2/dec_core/ai_core/sim_q2/sim_f2/kp`。
  - **验收**：解码输出 `frm_crc` 恒定、AI 输入 `ai_crc` 恒定、`ai_crc2==ai_crc`（推理期间无人踩输入缓冲）、同帧两次查询一致。
- **取证**（第二阶段：残留清零实验，假设被细化否定，2026-10-06 深夜）：验证"非确定性 = 读了上次运行残留的 arena"。基建：esp-dl `Model::zero_workspace()/poison_workspace()`（`root_reset()` 是库内现成但**全库零调用**的 arena memset）+ `{"cmd":"mode","feat_ws":N}` 三态运行时开关。

  | 配置 | sim_raw 跨度 | 结论 |
  |---|---|---|
  | ws=0 基线 | **0.89**（0.106~0.998） | 混沌全貌 |
  | ws=1 只清特征 | 0.37（簇状） | 改善但不确定 |
  | ws=1 检测+特征全清 | 0.86（0.133~0.997） | **kp 已稳定，输出仍乱跳** |
  | ws=1 全清 + C2M 回写 | ~1.0 | 缓存不一致变体也否定 |
  | ws=2 毒化 | 0.04 但 **~15s/帧** | 确有算子读 arena 非自己写的数据 |

- **取证**（第三阶段：逐层 dump 二分收口，2026-10-07 凌晨）：esp-dl 加 `Model::run_trace()` 按执行计划逐算子对**输出张量**做 CRC32（103 个算子），每帧跑 A/B 双 run。

  | 轮 | A/B 同帧双跑首分歧 | 跨帧首分歧 | 本帧 sim |
  |---|---|---|---|
  | 1 | #68 | （建立参照） | 0.9979 |
  | 2 | #9 | #9 | 0.9964 |
  | 3 | #8 | #68 | 0.4064 |
  | 4 | #13 | #13 | 0.2394 |
  | 5 | #4 | #4 | 0.9977 |
  | 6 | #2 | #0 | 0.9596 |

- **根因**（最终结论）：① **同帧两次 run 就分歧** ⇒ 排除一切跨帧状态/执行历史解释；② **首分歧算子逐轮随机** ⇒ 排除"某个内核实现有 bug"；③ 输入/kp/工作区全部 crc 级恒定 ⇒ 唯一自洽解释是**内存读出层在执行期随机分歧**（DSA/DMA/缓存交互竞态或 PSRAM 时序边际），**app 与模型内存卫生都无法修复**。
- **修复**（工程绕行，上游缺陷不可修）：F2 窗口投票（K=5/M=3）+ 快速通道 + **每次开机相对标定**；`feat_ws`/`run_trace` 基建保留、默认关。
- **验收**：回归 25/25 在投票 + 相对标定下稳定；真人 sim 稳定 0.82–0.94；跨 boot 绝对阈值明确**放弃**。
- **教训**（判据 P11/P15）：① 非确定性要先用 crc 指纹把"输入侧"排除干净，再谈算法；② 逐层二分的价值在于**排除**，不在找到；③ 上游硬件级缺陷只能用投票/标定在应用层吸收，并把它写进文档当成契约（`esp-dl_issue_draft.md`）。
- **被推翻的假设**
  | 假设 | 为什么错 |
  |---|---|
  | arena 残留被读 | 全清 + 回写后仍混沌 |
  | 检测子模型 kp 漂移带动特征漂移 | kp 已 crc 级稳定，输出仍乱跳 |
  | CPU 脏行 vs 算子直读（缓存不一致） | C2M 回写后仍混沌 |
  | 某个算子实现有 bug | 首分歧算子逐轮随机 |
  | "启动抽签/执行历史" | 同帧双跑即分歧 |

### C2 颜色"偏得离谱"：JPEG 链路红蓝对调，AI 路径却完全正确

- **现象**：白天画面颜色与人眼差距极大（黄→天蓝、橙红→深蓝、天蓝→黄、紫→橙红；黑白灰绿正常）。
- **取证**（分层裁决，顺序决定成败）：
  1. 用户实物四色实测 → 教科书级 **R/B 互换补色模式**（G 居中不动所以绿/灰/白不受影响）；
  2. **矩阵验算法**：取传感器原始值 → 乘 WB → 分别代入 `P·M`（CCM 输出行 R/B 互换）与 `M·P`（输入列互换）两种模型逐一验算，**四色全部吻合**（单纯 M 转置不吻合，排除转置嫌疑）；但两种都吻合 ⇒ **无法从颜色本身判断对调发生在哪一层**；
  3. **raw 直出裁决（5 分钟，决定性）**：同一场景同时抓 raw 与 JPEG —— raw 罐金黄/标记橙红/桌面暖棕（**摄像头路径完全正确**），JPEG 罐浅蓝/标记深蓝（**文件本身红蓝对调**）；PIL 与模拟器（tjpgd）**两个独立解码器**结果一致 ⇒ 排除解码端 ⇒ **硬件 JPEG 编码器对 RGB565 输入的通道序解读与标准相反**（驱动无配置项，`pixel_reverse` 只管字节序）。
- **根因**（两处独立缺陷叠加）：① **IPA 控制器关闭后，厂商标定 CCM 从未下发**（与当年 gamma/BF 丢失同因）——`esp_cam_sensor/sensors/sc2336/cfg/sc2336_default.json` 的 `acc/ccm/matrix = [1.408,-0.094,-0.314, -0.13,1.28,-0.15, -0.072,-0.173,1.245]`（三行和均为 1.0 = 亮度守恒，灰白不动只校色相）；下发走 `V4L2_CID_USER_ESP_ISP_CCM`（0x009810E0），且驱动里 `isp_reconfigure_white_blance()` 实际就是调 `isp_reconfig_ccm()`，WBG 按**列**缩放进 CCM（数学上等价"先 WB 后 CCM"），所以写 CCM 不会冲掉 WB。② **硬件 JPEG 编码器对 RGB565 输入的通道序解读与标准相反**（驱动无配置项，`pixel_reverse` 只管字节序）。
- **修复**：`app_stream.c` 编码前把 R/B 换回（RGB565 位域交换 / RGB888 首尾字节交换，私有缓冲顺带 stride 重排）；只影响 0x05 JPEG 链路，AI/raw 不经此处。代价：编码 **4ms → 44ms**（preview 10fps 可接受）。CCM 走 `app_camera.c` 的 `CAM_MREQ_CCM` + `isp_apply_ccm(mix)`（`M' = I + mix/1000×(M−I)`，钳 (-4,4)，0=禁用），init 里随初始 WB 一起下发默认 `CONFIG_APP_CAM_CCM_MIX`。
- **验收**：CCM 下发后**暗部与彩色物体色相正常**；用经验 WB 反解中性点得到的仍是 (1320,1645)，与厂商 CCM 配套自洽；R/B 换回后同一场景 JPEG 与 raw 直出不再呈现补色对调。
- **顺带修**：raw 帧 614KB 超过 netlink 单帧发送预算 100ms → 永远发不出（表现为"8s 收不到 0x05 帧"）→ `app_netlink.c` 预算提到 **500ms**。
- **教训**（判据 P13）：**"显示链路会说谎"** —— 此前所有基于 0x05 JPEG 的颜色观察与调参（WB 1320/1645、"高光偏粉"、CCM 效果评估）都隔着一次通道对调，结论全部作废。颜色类问题第一步永远是 raw 直出。另：CCM 切换后 AWB 要 10~30s 重收敛，A/B 前必须等稳定或临时钉死 `wb_kr/kb`。

### C3 AUTO 运动切换"卡顿 1~2 秒"：不是切换慢，是三层叠加

- **现象**：静态低光下 AUTO ON 效果最佳，但识别到运动物体切换帧率时明显卡顿 1~2s。
- **取证**：`af_ms` 一直 1~2ms（切换动作本身不慢）；板端日志实测 `auto-fps -> 50 fps` 后约 **950ms** 就 `auto-fps -> 2 fps`，每秒来回振荡 —— PC 看到的"卡顿"就是振荡。
- **根因**：AUTO 高帧率态靠"每 2s 开一个 ≤300ms 探测窗口"判断是否还在动；低帧率下窗口内**常常拿不到可用样本**，被当成"静止" ⇒ 立刻降回低档 ⇒ 又检测到运动 ⇒ 升档。
- **修复**：① `app_imgpipe` 新增 `mv_stats_us`（采样时刻）与 `mv_ready`（本样本是否来自**真实比较**，基准帧恒 0 不算）；② 探测窗口只在拿到可用样本或超时后才关，拿不到就**保持 50fps 不下结论**；③ 升档后加最短驻留 1.5s；④ 修单位（按 ms 比较，`× 1000`）；⑤ 保持时间在"单帧周期 > 保持时间"时跳过（夜视 1s/帧 ≫ 100ms）；⑥ `auto_fps_tick/night_tick/camauto_tick` 改**每轮主循环都跑**（含 `get_frame` 超时轮），只在拿到新帧才跑会把决策拖一整个帧周期；⑦ `auto_fps_set(false)` 把帧率**交还夜视阶梯**，手动 fps 命令改成"先关阶梯再退 AUTO"。
- **配套**：`Kconfig` `APP_CAM_NIGHT_FPS_MIN` **2 → 5**，因为实测 2fps 并不比 5fps 亮（`avg_luma` 3.2 vs 4.9、JPEG 20KB vs 31KB）——这一档没有亮度代价却放大升档延迟。
- **验收**（真机对照表）：

  | 指标 | 修复前 | 修复后（2fps 档） | 修复后（5fps 档，当前默认） |
  |---|---|---|---|
  | 50/2 来回振荡 | 每 ~1.5s 一次 | 无（120s 内只升档 1 次） | 无 |
  | 帧到达最大间隔 | 990ms | — | **389ms** |
  | 运动→升档端到端 | 4517ms | 2903ms | **1259ms** |
  | 其中"排写"段（决策→写寄存器） | 910ms | 910ms | 340ms |

- **教训**（判据 P9/P12）：① "有没有新样本"和"能不能据此下结论"必须两个字段；② tick 与 ms 混用；③ 状态机节拍不能挂在数据节拍上；④ 反直觉档位要抓帧裁决。

### C4 白天曝光余量阶梯 50→20→10fps 的四个坑

- **坑 1 AE 在量化边界打摆**（exp 500↔994、gain 0↔70）：瞬时值条件凑不齐保持时间 → 增益必须 EMA。
- **坑 2 `s_cam_exp_max` 开机是 0**（只有 cam 命令/切档才更新）→ 白天阶梯在第一个客户端连接前**永远早退**；已在主循环加一次性播种（`get_ctrl` 读真实上限）。
- **坑 3 观察窗口陷阱**：`watch 8` 在 25fps 下只覆盖 0.3s，而保持时间 5s → 点查询得出"没触发"的假结论。验证状态机要用**单连接长窗口探针**（`_cycle_probe.py`；注意 board 单客户端，watch 占线时 cmd 连不上）。
- **坑 4 人为压目标造成的假病态**：`ae_target=20` 在半亮房间会过曝到白（luma 252）→ 档位被踢回 tier0 → AE 又压暗 → 循环；真实夜晚 boost 不会过曝，**判定为不修**。
- **验收数字**：暗房间 ~15s 自动 50→**20fps**（exp 994/2494=40% 余量，luma 121，gain 64）；顶到 exp_max 250 后 20→**10fps**（2500/4994=50ms）；`ae_target=120` 恢复后正确停在 10fps（迟滞有效）；单帧进光 50fps 顶格 20ms/gain67 → 10fps 90ms/gain0（**4.5 倍进光、零增益**）。
- **另**：曾怀疑"帧率像重新爬阶梯 = 崩溃"，抓串口 60s 无 `rst:`/panic ⇒ 是有人动了灯（判据 P14）。

### C5 低光 26fps 把 H.264 砍成 13fps：喂帧相位 bug

- **现象**：上午 `camera: capture ... 50.0fps` → H.264 20~24fps；AE 拉满后相机只有 **26fps**，H.264 掉到 **13fps**。vflip 开/关 A/B 均 26/13，排除 Qt/云页/编码器外部因素（编码器 UART 自身就报 13fps）。
- **根因**：`jc_p4_app/main/app_h264enc.c:744` 用 `next_frame = now + FEED_INTERVAL(40ms)`（相对当前时刻重置），26fps 的帧间隔 38.5ms ⇒ 每两帧才编码一次。
- **修复**（按优先级）：① 先补正面光让相机回到 50fps（实测逆光下 exp 994/994、gain 129/192 仍不够，脸成黑剪影、MSRMNP 不出框）；② 要低照度也保帧率，则把喂帧改成**截止时间累加**（`next_frame += FEED_INTERVAL`，落后超一周期再重同步），需重刷。
- **教训**：帧率类问题先分"上游有没有帧"和"下游有没有按周期取帧"，两个都要有计数器；`now + interval` 与 `+= interval` 是两种语义。

### C6 ISP 的 YUV420 是 `O_UYY_E_VYY` 打包，不是平面 YU12

- **现象**：按平面 YU12 布局做 CPU 转换 / PPA 配置时，送检帧出来是**彩色噪声**；而 H.264 画面与 AE 的整帧均值都正常 —— 所以这个坑在只跑编码和只跑 AE 时**完全不暴露**。
- **取证**：读 `esp_h264_types.h:49` 与 `esp_video` 的映射 —— `V4L2_PIX_FMT_YUV420` 被直接映射成硬编的 `ESP_H264_RAW_FMT_O_UYY_E_VYY`：`line1: u y y u y y …`（偶行 U）、`line2: v y y v y y …`（奇行 V），行字节数 `w*3/2`、整帧仍是 `w*h*3/2`。
- **根因**：fourcc 名字相同，内存布局却是厂商特定的交错打包；平面假设只在"逐像素消费"的路径上才出错。
- **修复**：`app_yuv2rgb` 送检帧桥按 `O_UYY_E_VYY` 实现（结论记录于 `docs/library/H264重构交接与阶段计划.md` §13.2）。
- **教训**：**平均类指标（AE/亮度）掩盖布局错误**，只有逐像素路径能暴露；新增任何"按像素消费 YUV"的功能前，先用一帧落盘手工比对，而不是查 fourcc 文档。

### C7 相机倒置摆放时人脸检测为 0（MSRMNP 不处理 180° 人脸）

- **现象**：画面正常、检测 `0%` 检出，怀疑算法坏。
- **根因**：MSRMNP 对 180° 旋转人脸不出框；同场还有一次"0% 检出"其实是**镜头没对准人**（对着显示器/线缆）。
- **修复**：Qt 相机页加「垂直翻转」（`{"cmd":"cam","vflip":true}`，与 ISP 固定 HFLIP 合成 180°），勾选后 H.264 与送检帧同时转正，存 QSettings。
- **教训**（判据 P13 的近亲）：**排查画面异常先抓一帧**（`jc_test.py img`）看现场，再判断算法；不要凭结果帧数字推理。

### C8 上位机镜像字段用错，视频与送检反向

- **现象**：勾选"镜像"后画面反了但送检帧没反（或反之），且勾选状态被轮询立刻弹回。
- **根因**：YUV420 下 H.264 与送检帧都来自 ISP，`{"cmd":"cam","mirror":...}` 改的是 imgpipe 的 RGB565；正确字段是 `hflip`。另外只有 vflip 有 toggled 处理器，其余靠"下发相机参数"，而每帧 0x02 回填会立刻把勾选状态刷回板端旧值 ⇒ 表现为"点不动"。
- **修复**：全部勾选**即发即生效**（`toggled` 直接下发），镜像/垂直翻转存 QSettings（`cam/hflip`、`cam/vflip`）并在连接后补发；YUV420 固定 WB、AWB 保持关。
- **教训**：同类控件一次修完（不要只修一个复选框）；UI 状态与设备状态冲突时，**下发优先、回填不得覆盖用户刚改的值**。

## 6. D 章 · 数据一致性（face.db / 名表 / 快照）

### D1（深度，全文见 `docs/library/2026-10-29_face.db膨胀_槽号与下标错位_同名重注册零命中_修复记录.md`）face.db 只增不减

- **现象**：名单只有 1 人 / 5 条特征，导出却要传 40~90KB；导出超时"分片接收超时：已收 49152/98538 B"。
- **取证**（本机留存信封逐字节解析）：`snap_now.bin` total=20/valid=5（41138 B）、`snap_now2.bin` 45/10（92503 B）、`snap_fail.bin` 28/5（57538 B）；压实后 `snap_compacted.bin` 5/5（**10383 B**）。
- **根因**：`enroll_feat()` 永远 `fseek(SEEK_END)` 追加并 `num_feats_total+1`；`delete_feat()` 只把槽号写 0、**`total` 与文件长度都不变**（`esp-dl/esp-dl/vision/recognition/dl_recognition_database.cpp:133-160` / `:170-200`）。
- **修复**：`db_compact()`（重写有效特征为连续 id 1..n，名表 old→new 重映射，动盘前 `db_backup_current()`，写 `face.tmp` 再 `remove`+`rename`，阈值 `DB_COMPACT_HOLE_MIN=4`）在 boot 与每次删除后触发；0x06 分片重试 4 次，仍失败明确报 `export aborted: N/M part(s) unsent`。
- **验收**：同一份库 `98538 B / 7 片（超时）` → `10383 B / 1 片（一次成功）`。
- **教训**：**"删除后导出还是删除前大小"是格式行为，不是时序竞争** —— 这个误解差点让 900ms 自动同步延时被"修"掉。

### D2 `query_feat()` 返回下标而不是槽号（本手册最重要的一个上游缺陷）

- **取证**：`dl_recognition_database.cpp:251-258`

  ```cpp
  int i = 1;
  for (auto it = m_feats.begin(); it != m_feats.end(); it++, i++) {
      sim = cal_similarity(it->feat, (float *)feat->data);
      if (sim <= thr) continue;
      // results.emplace_back(it->id, sim);   ← 上游注释掉的正确实现
      results.emplace_back(i, sim);           ← 实际返回 m_feats 的 1-based 下标
  }
  ```

  加载时 `id==0` 的空洞被跳过不入 `m_feats`（`:94-109`）⇒ **只要库里删过一次，下标就 ≠ 槽号**。
- **现象**：`raw 0.917 · 票数 3/3 · stable 1` 全部正常，但 `top1槽 1`；名表在 `6..10` ⇒ 查不到名字 ⇒ 判 reject。**相似度再高也没用**。
- **根因**：上游返回遍历下标，而 `m_feats` 只装有效特征（空洞不入列），删除一次其后全部前移；名表按**槽号**建 ⇒ 两侧口径不同源。
- **修复**：板端自建 `下标→槽号` 映射（`s_id_of_index[]` + `db_rebuild_id_map()` + `db_slot_id()`，`app_faceai.cpp:789/792/820`），在 boot/dbx/testlib/clear/registered/deleted/compact 后全部重建；三个消费点（主脸 `:1746`、副脸 `:1503`、注册去重 `:1644`）一律换算。
- **验收**：压实后重注册拿到 id 6–10（下标 1–5）→ **立刻稳定报名字**；`resync(registered)` 打印 `file total=10 valid=5 | mem=5 names=5` 两侧一致；10-29 用户实测「重复注册都能稳定识别」。
- **教训**（判据 P5/P15）：不打补丁的前提下，**用"下标→槽号"表把上游缺陷包在适配层里**，比改第三方库稳；映射表的重建点必须穷举所有会改变 `m_feats` 的路径。

### D3 注册名字绑错槽位：personB 被签到成 personA

- **现象**：云端快照 `#4` 里 `total=30 valid=17`，名表只有 5 条且全是 `personA`（id 13–17），`personB` 的槽 14 被顶掉；personB 的特征仍参与匹配 ⇒ **personB 站镜头前会写成 personA 的签到记录**（比"识别不到"更糟）。
- **取证**（`_dev/cloud_snap3.bin` vs `cloud_snap4.bin` 逐字节比对，本次复算）：`#3` = 22 槽 / 9 条有效特征（id 14–22）/ 名表 `[{14:personB}]`；`#4` = 30 槽 / 17 条（id 14–30）。**`#3` 的 9 条特征在 `#4` 的同一槽位上逐字节相同（9/9）**，新增注册实际落在 **id 23–30（8 条）**，名表却写成 `13,14,15,16,17 → personA` —— 特征一个没动，**同一个槽 14 的名字从 personB 变成 personA**。
- **根因**：注册分支用 `query_feat(f, 0.999f, 1)` "反查刚分配的 id"；同人旧特征彼此本就 >0.999 ⇒ 查到的是**老槽位**，`name_add` 改写原条目。
- **修复**：改为板端自算 —— `enroll_feat()` 前后各读一次 face.db 头，断言 `after == before + 1` 才取 `id = after`（`db_read_feat_total()`）；不一致回 `event="error" msg="id mismatch"` + `reg_rollback()`；`name_add()` 拒绝跨人覆盖（`ESP_LOGE "id %u already owned by '%s'"`）。
- **教训**（判据 P18）：数据正确性 bug 出现时**禁止用"再注册一次"补救**；先用逐字节取证把 id 归属钉死。

### D4 注册中断残留无名孤儿特征

- **现象**：快照 #4 里 17 条有效特征只有 5 条有名（**13 条孤儿**）。
- **根因**：`names_save()` 只在采满时执行，而每帧 `enroll_feat()` 已落盘。
- **修复**：会话记录 `s_reg_ids[]`；被新 `register` 抢占/出错时 `reg_rollback()`；启动 / `testlib` 切换 / `dbx` 导入后 `lib_gc_orphans()` 回收"有特征没名字"的槽。
- **教训**：GC 必须**先读完 id 列表再删**，否则与 `delete_feat` 交叉读写同一个 FATFS 文件；`CONFIG_APP_FACEAI_MAX_FEATS=320`，所以这是**正确性**问题而不是容量问题。

### D5 face.db 头损坏 → `65535 feat(s) in lib`

- **现象**：清库后复位，启动日志报 `65535 feat(s) in lib`，随后注册/识别全部异常，且 esp-dl 只打一行 `Feature len in storage does not match feature len in db.` 就继续跑（构造函数的错误被吞）。
- **取证**：`_dev/clean_check.log:243-244`：`E dl::recognition::DataBase: Feature len in storage does not match feature len in db.` 紧跟 `I faceai: feature db /storage/face.db: 65535 feat(s) in lib, name table 0`。
- **根因**：`clear` 的 `remove` + 重建被复位打断，留下全 `0xFF` 头；esp-dl 构造函数吞掉错误，`total` 读出 65535（远超 `MAX_FEATS=320`）。
- **修复**：`db_ensure_healthy()` 校验头三元组（`feat_len==512`、`total≤320`、`valid≤total`），坏头直接重建空库并转发 `faceai: ⚠ face.db 头损坏(...)，已重建为空库`；在 boot/`clear`/`dbx` 都查。
- **验收**：10-28 20:56 再清一次后启动回到 `0 feat(s) in lib, name table 0`（`_dev/heal_boot.log:245`）。⚠️ **`db_ensure_healthy` 的自愈分支至今没有真实触发过**（所有抓取里都没有 `头损坏` 那行）—— 它属于纵深防御，**不能写成"已验证"**（见第 9 章口径）。
- **教训**：外部库"看起来初始化成功"不等于数据可信；**对上盘结构做三元组校验**是廉价且必要的。

### D6 `esp_err_t` 隐式转 bool，真值恰好相反

- **现象**：改完"注册槽号自算"后**每一次注册都报 `id mismatch`**（用户当场复现）。
- **根因**：`const bool have_after = db_read_feat_total(&after);` —— `esp_err_t` 是整型，`ESP_OK=0 → false`、`ESP_FAIL=257 → true`。
- **修复**：`(db_read_feat_total(&after) == ESP_OK)`。
- **教训**（判据 P5）：C 语义坑只能靠"写的时候就不依赖隐式转换"来防；返回 `esp_err_t` 的函数一律显式比较。

### D7 JCDF 信封内没有尾部 CRC，解析工具把最后一个 float 截掉

- **现象**：特征范数/nan 检查里最后一条特征的末位 float 总是异常。
- **根因**：工具假设信封末尾 4 字节是 CRC。实测 `10383 = 16(信封头) + 111(names) + (6 + 5×2050)` 整除无余量 ⇒ **信封内无 CRC**，CRC32 只随 `db_export` 的 ack 单独走。
- **修复**：`_dev/feat_inspect.js` 按槽数截断，不再 `b.length-4`。
- **教训**（判据 P2）：取证工具自己也要被验证；工具的错会把你引向"固件有 bug"的错误结论。

### D8（深度）删除后同名重注册 → 100% 零识别：三个缺陷的合体

- **现象**（复现步骤，每次成立）：① 某人已注册 5 帧、稳定识别 → ② 删除他 → ③ 同名重注册 5 帧（`registered`、名单 `1 人 / 5 条特征` 数字都对）→ ④ 站镜头前**一帧都不报名字**，`sim` 高达 0.91–0.95 也判 reject，且无任何告警 → ⑤ **清空库后重注册又正常**。
- **取证**（同一时刻两侧对齐，决定性）：磁盘 `snap_after_reg.bin` = `total=10 valid=5`、**pos1-5 全 0、pos6-10 = id 6-10**、名表 `6..10=personA`（完全自洽、无孤儿）；实时遥测 `top1槽 1 · raw 0.917 · 票数 3/3 · stable 1 · 结论 none`。
- **根因**：D2（下标当槽号）。第 ⑤ 步"清空就好"是关键线索 —— 清空后无空洞，下标恰好等于槽号。
- **修复**：D1+D2+D5 的组合（映射表 + 压实 + 头自愈 + 强制 `db_resync_from_disk`）；Qt 侧分片容错、空闲看门狗、日志降噪、自动同步补试。
- **验收**：第二个人注册后拿到 id 24–28（列表下标 6–10，正是过去必挂的场景）→ **立刻稳定报名字**；`resync(deleted) file total=10 valid=5 | mem=5 names=5` + `compact(deleted) 槽位压实 -> 5 条连续槽，名表 5 条`；用户 10-29 实测确认「重复注册都能稳定识别」。
- **教训**（P2/P3/P4 的合体）：① 一侧看磁盘、一侧看遥测，**同时刻对齐**才能定位；② "清空就好"这类恢复性观察要当成线索记录，不要当成"已经好了"；③ 观测手段要**先于**修复上线，否则每一轮猜测都在重新发明轮子；④ 上游缺陷要在适配层吸收并穷举重建点，不要指望打补丁。
- **被推翻的假设**
  | 假设 | 为什么错 |
  |---|---|
  | 槽号与 face.db 磁盘位置脱钩 | `enroll` 恒在 `pos=total` 追加且 `id=total+1`，位置↔槽号恒等（`snap_fail.bin` pos24-28=id24-28） |
  | 给 esp-dl 打补丁返回真实 id | 无 remote 的 gitlink，补丁进不了版本库，干净克隆会缺函数编不过 → 10-27 完整回退 |

## 7. E 章 · 上位机与 UI 自动化

### E1 一次导出卡住后库任务永久"忙"，只能重启程序

- **现象**：一次 `db_export` 没走完（始终没有"✓ 导出成功"）后，注册/删除触发的自动同步和手动上传全部静默失败，只报 `⚠ 板端库任务忙，请稍后再试`，**必须重启上位机**。
- **根因**：忙标志没有超时复位；`disconnect()` 也不结束在途任务。
- **修复**：`LinkSession::DbJob` 加单发 `watchdog` —— 导出 ack 后与每个合法分片 `dbArmWatchdog(8000)`、导入每 tick 20000，超时 `dbFinish(false,"分片接收超时：已收 x/y B")`；`disconnect()` 让在途任务以 `链路断开，库任务中止` 结束并停掉抓帧定时器。
- **验收**：`registered` → 自动同步链路恢复（`#6` 就是这么上传的）；导出实际 <1s 完成，超时分支未能脚本级复现。
- **教训**：① 任何"忙/进行中"标志都必须配超时或断链复位，否则一次异常就永久锁死（同一模式在 F3 里以另一种形态复现）；② **测不出来的分支要如实写"未复现"**，不要写成"已验证"（第 9 章口径）。

### E2 分片越界判死整次导出

- **现象**：上一轮导出的尾巴混进新一轮，Qt 直接判整次失败。
- **根因**：0x06 分片协议没有"本轮开始"的显式边界，上一轮未收完的残留分片会落进新一轮的偏移表里；Qt 把"偏移不合法"一律当成协议错误。
- **修复**：`link_session.cpp:295-304` 跳过越界/非单调偏移的分片并计数（`m_db.stray`），成功消息里带 `忽略 N 个残留分片`。
- **教训**：流式协议要把"可容忍脏数据"和"必须失败的错误"分开，别用一个计数器管两件事。

### E3 UIA `AutomationId` 是完整点分路径，按索引点按钮会点错

- **现象**：命中率采样脚本两次返回 0 样本，一度误判"脚本坏了"；另一次自动化把「上传」点成了「截图」。
- **根因**：① Qt 控件的 `AutomationId` 形如 `QApplication.MainWindow...QWidget.diagVote`，`-eq 'diagVote'` 永远匹配不到；② 按固定索引取按钮，会因当前页不同而落到别的控件；③ 无人入镜时占位标签文本里没有 `stable`，采样自然为空。
- **修复**：给 QLabel `setObjectName("diagVote")` 造稳定锚点 + 匹配用 `.EndsWith('diagVote')`；改用 `_dev/qt_click_name.ps1`（按首字 charcode + enabled 状态定位）；脚本一律 ASCII-only。
- **另**：**QMessageBox 二次确认框和原生文件对话框的按钮都抓不到**（UIA 里进程顶层窗口数恒为 1，对话框是主窗口的子节点），`%y` 快捷键也不可靠 ⇒ 这类步骤交给用户手点，规划时就要写进去。
- **教训**：自动化返回 0 样本时，**先怀疑锚点与占位文本，再怀疑被测系统**；两次"脚本坏了"的误判都源于没区分"控件不存在"和"控件文本还没变成期望值"。

### E4 boot 期与运行期的可观测性冲突

- 见 B6（boot 不发 USB 日志）与 F2（日志降噪）：同一类问题的两端 —— 上位机侧 `setMaximumBlockCount(500 → 2000)`，并在 `logLine` 里丢弃以 `imgpipe` 开头的统计行（只留状态栏）。

### E5 命令 ack 洪泛导致 `cmd_and_wait` 取错帧

- **现象**：读回来的数值离谱且不可复现。
- **根因**：流开着时 0x02 结果帧洪泛；`protocol.py` 早期把任意 0x02 当 ack。
- **修复**（`pc_host/protocol.py`，回归 harness）：ack **按命令名精确匹配**；读结果帧时跳过带 ack 的帧；脚本连 `127.0.0.1:13333` 不直连。
- **教训**（HANDOVER §4.7）：**先修 harness 再动固件** —— 本项目第 22 节第 1 条就是这个顺序，事后证明是对的。

## 8. F 章 · 云端与网络

### F1（深度）30 分钟去重被乱序补发击穿 → 对称 ±窗口

- **现象**：生产库里 `#18 09:53` 与 `#15 10:06` 两条 personA 事件，间隔 13 分钟同时入库（窗口应是 1800s 判重）。
- **根因**：为处理"晚到的旧事件"把窗口改成"只回看 `ts-window .. ts+60`"，而**断网补发必然乱序** —— 新事件先到并入库，旧事件后到时它的回看窗口看不到"比自己新的那条"，于是两条都通过。
- **修复**：`cloud_server/app.py` 改回对称窗口 `recent_event(con, person, device, ts-window, ts+window)`，并在代码里写明"乱序补发"这个理由；`/api/health` 暴露 `dedup_window_s`；Qt `CloudClient::dedupWindowS()` 读它，本地静默 = `min(server, 30min)`（未探到仍 5s）。
- **验收**：测试实例用"先 now 后 now-13min"探针回归 —— `newer-first` 入库、`older-later` 返回 `dup:true` 且**照片文件数不变**（判重发生在写照片与 `insert_event` 之前 ⇒ 抓拍一并过滤）；测试实例恢复 10s。
- **教训**：任何"时间窗口"语义都要先定义**乱序输入**下的行为；去重要同时覆盖事件与抓拍，否则留下"事件没了、照片还在"的脏数据。

### F2 日志面板被周期统计冲走 ⇒ 故障现场无法回溯

- 见 P4/P7：`imgpipe`/`imgpipe/prof` 每秒十几行把面板刷干净，本次排查**多次**因为拿不到历史行而返工。修复即 E4 的两处。

### F3（深度）注册后自动同步可能一次都不触发

- **现象**（10-29 11:27:43 实测）：注册 `zzzzzzzzzzzzzz` 5 帧，板端 3s 后就稳定报名字（签到 `#21 sim=0.913`），但 Qt 日志里**既没有 `← registered`，也没有 `☁ 名单已变化，自动同步人脸库…`**，也没有补试行；云端停在 `#32 · 1 人 / 5 特征`，直到手动上传才得到 `#33 · 2 人 / 10 特征 / 20799 B`。
- **根因**：自动同步只由 `registered`/`deleted` 这**一条 0x02 结果帧**触发（`main_window.cpp:1424-1430`），而 `send_result()` 把 `app_usb_link_send()` 的返回值**直接丢弃**（`app_faceai.cpp:1255`）—— 0x02 在 `cdc_write()` 走 500ms 预算，FIFO 连续满超预算即 `ESP_ERR_TIMEOUT` 静默丢帧，不重发。E1 的"失败补试"救不了：它只覆盖**已启动但导出失败**的任务，这里任务根本没被创建。
- **影响**：云端人脸库静默落后板端，不报错、不提示。删除侧同日一次成功，但丢帧条件相同，理论上一样会漏。
- **修复**：**未实施**（用户明确选择只记录不修）。候选修法（按侵入性排序，均未实现）：① `send_result()` 检查返回值，对名单变化类事件失败重发；② **Qt 定期读板端名单指纹（`list` 人数/条数哈希）比对，变了就同步**（推荐，唯一能在静默丢帧下自愈且不动固件发送策略）；③ `register` ack 后主动轮询一次 `list`。
- **验收**：不适用（未修）。当前口径靠人工观察：注册后日志必须有 `☁ 名单已变化`，否则云端就是旧的。
- **教训**：① **事件驱动的上层逻辑必须有轮询兜底** —— 单条 best-effort 帧丢一次就永久不同步，且没有任何告警面；② 与 E1 同形：**"没触发"和"失败了"是两类故障**，补试逻辑只管后者；③ 返回值被丢弃的地方，故障一定静默（P5 的运维版推论）。
- **临时规避**：注册后看日志有没有 `☁ 名单已变化`，没有就手动点一次「上传人脸库」。

### F4 公网 8080 不通 = 控制台防火墙，不是服务

- **取证顺序**：本机 `curl /api/health` → `ssh` 后 `curl 127.0.0.1:8080/api/health`。服务端 firewalld inactive、iptables 全 ACCEPT ⇒ 公网不通即 SWAS 控制台防火墙。
- **依赖**：放行按**出口 IP**，而本机出口 IP 天天变（<EGRESS_IP_A> → <EGRESS_IP_B> → <EGRESS_IP_C> → <EGRESS_IP_D>），已放宽到 `<办公网出口段>/24`；⚠️ **落在已放行网段内也可能不通**，要核规则本身。取真实出口 IP 的可靠办法：`ssh root@<server> 'echo $SSH_CLIENT'`。
- **纪律**：改服务器配置用 `sed` + `systemctl restart`，**绝不重新生成 Token**；`GET /api/facebank/latest?id=N` 可重取历史快照。

### F5 测试数据污染生产云 → 独立测试实例 + 测试固件 + 测试页

- **做法**：固件 `APP_FACEAI_PC_TEST`（默认 n；测试构建含 `0x01/src=pc` + `testlib` + `/storage/ftest.*`，生产构建裁掉）；Qt `QT_HOST_PC_TEST`「PC测试」页（原图直接作 `photo_b64`、独立 spool、测试模式阻断生产上报）；云端 `install.sh --test` 起独立 18080 实例（loopback、独立 data/token）。
- **验收**：测试库 25/25、Qt 注册/识别 `match 0.923`、原图 20347B 与测试云快照 2101B 均逐字节正确，**生产云人员/事件未变**；板子回生产固件后 `src pc`/`testlib` 被拒。

### F6 云端没有"删除快照"的 API

- **现象**：用户要求"把板端和云端的特征库全部清除"，服务端无对应接口。
- **根因**：服务端设计上只做了"上传/取最新/取指定版本"，**没有删除快照的 API**；而用户诉求是一次"彻底清库"。
- **修复**（无 API 时的做法）：进服务器直接操作 SQLite（`DELETE FROM facebank_snapshots` / `DELETE FROM persons`），删前 `cp /root/facecheck.db.bak_<ts>`；**签到事件与抓拍照片按用户措辞保留**。快照按设备保留最新 5 份（`snapshots_keep`）。
- **教训**：运维类需求要先确认"接口能力边界"，不能假设有 API；破坏性库操作必须就地备份。

### F7 用 COM3 观察运行期 = 自毁现场

- **现象**：两轮真人测量结果莫名其妙（一条 `→ 注册` 发进了死链路）。
- **根因**：打开 COM3 会拉 DTR/RTS **复位板子**，同时 Qt 持有的 COM5 句柄失效。
- **修复**（操作纪律，不改代码）：运行期观测一律走 0x04 日志帧 + Qt 日志面板；只有要抓启动日志/烧录时才用 COM3，用完必须重启上位机重连。需要主动复位时用 `_dev/reset_com3.ps1`（DTR/RTS 脉冲）而不是开新串口句柄。
- **教训**：任何"只是看一眼"的串口操作在这个板子上都是**写操作**；测量作废不会报错，只会给你一组看似合理的数 —— 所以每轮真人测量前要确认链路是活的（Qt 状态栏 + `link` 计数在涨）。

## 10. 硬件联调纪律

1. **一个客户端连板**：中枢/模拟器/脚本三选一；中枢在跑时脚本连 `127.0.0.1:13333`；网口不可用时回归可走 USB（`--serial COM5`）。
2. **端口角色固定**：COM3=CH340（烧录/启动日志，**开即复位**）、COM5=JCLINK 数据。重插后号会变，用 `GetPortNames()` 现查。
3. **不要用 COM3 观察运行期**（F7）；运行期观测走 0x04 + Qt 面板。
4. **相机档位与光照是变量**：测吞吐/帧率前钉死档位（P8），真人测试前先看 AE（L6）；逆光下 exp/gain 顶满也救不回来，先加正面光。
5. **Kconfig 试验只在 `_dev` 下**（`_dev/sdkconfig.m2`、`sdkconfig.pctest`），**严禁 `git checkout/stash` sdkconfig**；生产重建要能自动避开已知炸点（`HW_H264` 在 `sdkconfig.defaults` 里保持注释，见 A8/A2/B1）。
6. **热改编码器参数前先停识别**，或者干脆不热改（A4）。
7. **备份先行**：跑回归前 `db_backup x.bin`；覆盖式导入前板端自动存 `face_bak.db`+`names.bak`；云端库操作前 `cp` 一份 SQLite。
8. **构建脚本三问**（P16/B7）：跑在哪个区？退出码真的吗？日志落在哪？
9. **UI 类修复一次修全同类控件**，且勾选必须即时生效、持久化，不被轮询回填弹回（C8）。
10. **命令要能直接粘**：先声明权限与参数类型，附验证步骤与错误码分支；需要用户手点的环节（文件对话框、二次确认）要明说（E3）。
