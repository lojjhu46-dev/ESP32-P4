# 2026-10-28/29 修复记录：face.db 只增不减 · 槽号与下标错位 · 同名重注册 100% 零命中

> 一句话结论：**三个现象是同一条链上的三次发作。** esp-dl 的 `face.db` 按"槽位"存特征，`enroll_feat()` 永远追加并把 `num_feats_total` +1，而 `delete_feat()` 只把槽号写成 0、`total` 与文件长度都不动；它的 `query_feat()` 返回的又**不是槽号，而是内存向量 `m_feats` 的 1-based 下标**（上游把正确那行注释掉了）。名表按槽号建，于是库里只要出现过删除，下标就与槽号错位 —— 拿"第 1 条"去查名表必然查不到，表现为「删掉同名重注册后一帧都不报名字」，同时 face.db 体积单调膨胀到导出链路都发不完。

- 日期：2026-10-28 发现并复现 → 2026-10-29 定案并验收
- 涉及端：板端固件 `jc_p4_app/main/app_faceai.cpp`（主要改动）+ 上位机 `qt_host`（观测与容错）；`esp-dl` **只读定位、未打补丁**
- 修复提交：`f3fb858`（10-27 注册槽号改板端自算 + 孤儿回收 + 看门狗 + 云端去重）、`f965367`（10-29 下标→槽号映射 + 槽位压实 + 头自愈 + 导出重试）
- 阶段结论在 [`docs/library/H264重构交接与阶段计划.md`](H264重构交接与阶段计划.md) §15.9 / §15.10；本文补的是**取证过程、被推翻的假设和可复用判据**

## 1. 三个现象的准确描述

### 1.1 face.db 体积异常膨胀（只有 5 条特征，文件 57KB–92KB）

用户视角：「名单」页只有 1 人 / 5 条特征，但「上传人脸库」要传几十 KB，10-29 之后稳定是 10383 B。实测取证（本机 `_dev/` 里留存的导出信封，逐字节解析）：

| 时间 | 文件 | 信封 | `total` 槽 | `valid` 特征 | 磁盘上的真实槽号 |
|---|---|---|---|---|---|
| 10-28 20:23 | `snap_now.bin` | 41138 B | 20 | 5 | 16–20 |
| 10-28 20:33 | `snap_now2.bin` | 92503 B | 45 | 10 | 36–45 |
| 10-28 21:06 | `snap_fail.bin` | 57538 B | 28 | 5 | 24–28 |
| 10-29 09:45（压实后） | `snap_compacted.bin` | 10383 B | 5 | 5 | 1–5 |
| 10-29 09:56（再注册） | `snap_after_reg.bin` | 20634 B | 10 | 5 | 6–10 |

直接后果：`db_export` 要切成 7 片（0x06，每片 ≤16 KB）才能发完，链路一拥塞就半途超时：

```
[09:09:56] [板端] faceai: db_export 98538 bytes (7 parts) crc=0db43992
[09:10:04] ✗ 分片接收超时：已收 49152/98538 B
[09:10:04] ✗ 云签到：板端导出失败
```

### 1.2 内存号与磁盘槽号不一致 → 名字绑错人（更危险的那次）

`cloud_snap4.bin`（云端快照 #4）实测：`total=30 valid=17`，名表只有 5 条且全是 `personA`（id 13–17），`personB` 的槽 14 被顶掉；17 条有效特征里 **13 条无名**。危险之处在于 **personB 的特征仍参与匹配，但名字是 personA → personB 站到镜头前会被签到成 personA**，写进云端的是假记录，比"识别不到"更糟。

### 1.3 删除后同名重注册 → 百分百不识别（本次主 BUG，可稳定复现）

复现步骤（用户实测，每次成立）：

1. 某人已注册 5 帧，**能稳定识别**；
2. 「名单」页选中他 → 删除（板端回 `deleted 5 feat(s) of personA`）；
3. 同名重新注册 5 帧，板端回 `registered`、`名单：1 人 / 5 条特征` 数字都对；
4. 人站在镜头前，**一帧都不报名字**，`sim` 高达 0.91–0.95 也判 `reject`，且没有任何告警；
5. 「清空库」后重注册又恢复正常 —— 这条"清空就好"是关键线索：**只要库里没有空洞就正常**。

### 1.4 附带发现：face.db 头损坏会让整库静默失效

`clear` 的 `remove` + 重建被打断（复位）会留下全 `0xFF` 的头，esp-dl 构造函数吞掉错误：

```
E (8714) dl::recognition::DataBase: Feature len in storage does not match feature len in db.
I (8716) faceai: feature db /storage/face.db: 65535 feat(s) in lib, name table 0
```

`total=65535` 远超 `CONFIG_APP_FACEAI_MAX_FEATS=320`，后续所有读写都是未定义行为。

## 2. 机制底座：face.db / JCDF 到底怎么存

**face.db**（`esp-dl/vision/recognition/dl_recognition_database.cpp`）：

```
偏移 0    : database_meta = u16 num_feats_total | u16 num_feats_valid | u16 feat_len   （6 B）
偏移 6+r*2050 : 第 r 个槽 = u16 id + 512 * float                                        （2050 B/槽）
```

四条决定性行为：

| 函数 | 位置 | 行为 | 推论 |
|---|---|---|---|
| `DataBase()` 加载 | `:94-109` | 遇到 `id==0` 的槽**跳过不入 `m_feats`** | `m_feats` 只含有效特征，槽号有空洞时**下标 ≠ 槽号** |
| `enroll_feat()` | `:133-160` | `id = num_feats_total + 1`，改写头，`fseek(SEEK_END)` 追加 | **槽号恒等于"文件内第几条记录 +1"**，与是否删过无关 |
| `delete_feat()` | `:170-200` | 从头里 `num_feats_valid--`，把偏移 `6+2050*(id-1)` 的 id 写 0 | `total` 和文件长度**都不变** → 文件只增不减 |
| `query_feat()` | `:251-258` | 见下 | **返回下标，不是槽号** |

```cpp
int i = 1;
for (auto it = m_feats.begin(); it != m_feats.end(); it++, i++) {
    sim = cal_similarity(it->feat, (float *)feat->data);
    if (sim <= thr) continue;
    // results.emplace_back(it->id, sim);   ← 上游注释掉的正确实现
    results.emplace_back(i, sim);           ← 实际返回 m_feats 的 1-based 下标
}
```

**JCDF 信封**（板端导出格式）= `magic "JCDF"(4) + ver(4) + face_len(4) + names_len(4)` + names JSON + face.db 原文；**信封内部没有尾部 CRC**，CRC32 只随 `db_export` 的 ack 单独走。早期 `_dev/feat_inspect.js` 按"末尾 4 字节是 CRC"切片，把最后一条特征截掉了 —— 这是纯工具 bug，别误判成固件问题。

## 3. 实际修复流程（时间线，含被推翻的假设）

### 阶段 1 · 逐字节取证，先证明"名字写错行"而不是"识别不到"

不猜，直接把每次 `db_export` 的信封解析成 `{槽号 → 特征字节}` + 名表，比对注册前后：`_dev/verify_snapshot.js`（比对参考快照）、`_dev/snap_peek.js`（单份结构）。结论：新注册 5 帧实际落在 id 23–30，名表却写成 `13,14,15,16,17 → personA` —— **`name_add()` 被喂了错的 id**。

错误入口在注册分支：用 `query_feat(f, 0.999f, 1)` "反查刚分配的 id"。同一个人的旧特征彼此相似度本来就 >0.999，反查到的是**老槽位**。

### 阶段 2 · 第一次修复：槽号改由板端自算（不碰 esp-dl）

`enroll_feat()` 前后各读一次 face.db 头，用 `after == before + 1` 断言追加确实发生，取 `id = after`：`db_read_feat_total()` [app_faceai.cpp:596](../../jc_p4_app/main/app_faceai.cpp#L596)、调用点 `:1659-1671`；不一致就 `event="error" msg="id mismatch"` + `reg_rollback()`（`:573`）。名表加护栏 `name_add()` 拒绝跨人覆盖。

> ⚠️ 这次修复当场踩了个 C 语义坑，值得单列：
> ```cpp
> const bool have_after = db_read_feat_total(&after);   // ✗ esp_err_t 是整型
> ```
> `ESP_OK = 0` → `false`，`ESP_FAIL = 257` → `true`，**真值恰好反了**，结果每一次注册都报 `id mismatch`。用户当场复现后才发现。正确写法 `(db_read_feat_total(&after) == ESP_OK)`。

同时补上 1.2 的另一半：`names_save()` 只在采满时执行，中断即留无名孤儿 → 会话记录 `s_reg_ids[]`（`:243`）、被打断/出错 `reg_rollback()`（新 `register` 抢占时也回滚，`:3090`）、启动/`testlib`/`dbx` 后 `lib_gc_orphans()` 回收（`:699`）。

### 阶段 3 · 加观测：把"查名表那一行"变成看得见的遥测

改完仍然偶发不识别，而日志里什么都看不见 —— 于是先做观测，再改代码。板端结果帧新增 4 个字段 `votes / need / win / rid`，Qt 识别页顶部横幅 `diagVote`（[main_window.cpp:793](../../qt_host/src/main_window.cpp#L793)、`updateVoteDiag()` `:1442-1466`，500 ms 节流）+ 卡投票告警 `:1469-1476`；同时把日志环形缓冲 500→2000 行并丢弃 `imgpipe*` 周期统计（`:241-245`、`:459`）—— 此前每秒十几行统计把面板冲干净，**故障现场根本无法回溯**（本次排查多次受害，`_dev/qt_bug.txt` 里能看到满屏 `imgpipe/prof`）。

投票也在这一步改成**按人计票**（A 方案）：`smooth_rec_t{id,sim,key}` `:250`、`smooth_key()` 对名字做 FNV-1a `:488`、`smooth_tally()` 按 key 归并取桶内最高 sim 作代表 `:511`。此前按特征 id 计票，一人多条特征会把票数稀释到永远不过 `M=3`。
### 阶段 4 · 决定性证据：内存说槽 1，磁盘说槽 6–10

压实后（`snap_compacted.bin`：1–5）再注册 personA 5 帧，删除留下的空洞使新状态变成 `snap_after_reg.bin`：`total=10 valid=5`、**磁盘 pos1-5 全 0、pos6-10 = id 6-10**、名表 `6..10 = personA`（完全自洽，无孤儿）。同一时刻实时遥测：

```
top1槽 1 · raw 0.917 · 票数 3/3 · stable 1 · 结论 none
```

`raw 0.917` 说明特征匹配极好，`票数 3/3 / stable 1` 说明确认逻辑正常，唯一错的是 **`top1槽=1`** —— `query_feat` 返回的第 1 条下标被当成槽号去查名表，查不到，于是判 `reject`。**根因当场定案：不是槽号与磁盘脱钩，是 esp-dl 返回下标。**

修复：板端自建 `下标→槽号` 映射表 `s_id_of_index[]` `:789` + `db_rebuild_id_map()` `:792` + `db_slot_id()` `:820`，在 boot / `dbx` / `testlib` / `clear` / `registered` / `deleted` / `compact` 之后全部重建，**三个消费点**（主脸匹配 `:1746`、副脸 `:1503`、注册去重 `:1644`）一律换算。

### 阶段 5 · 兜住膨胀与坏头，并让链路能自愈

| 改动 | 位置 | 作用 |
|---|---|---|
| `db_compact()` 槽位压实 | `app_faceai.cpp:2441`（阈值 `DB_COMPACT_HOLE_MIN=4` `:2439`） | 有效特征重写成连续 id 1..n、名表按 old→new 重映射；**动盘前先 `db_backup_current()`**（`:2423`），写 `face.tmp` 再 `remove`+`rename`（`:2490-2502`）；boot（`:3748`）与每次删除后（`:3131`）触发 |
| `db_ensure_healthy()` | `:666` | 校验头三元组（`feat_len==512`、`total≤320`、`valid≤total`），坏头直接重建空库并转发 `faceai: ⚠ face.db 头损坏(...)，已重建为空库`；boot / `clear` / `dbx` 都查 |
| `db_resync_from_disk()` | `:618` | 注册/删除后打印 `resync(...) file total/valid vs mem/names` 并强制从磁盘重载 → 内存号不可能再与磁盘分叉 |

### 被推翻的假设（都曾被当成结论写进过记录）

| 假设 | 当时看着像的理由 | 为什么错 |
|---|---|---|
| 「槽号与 face.db 磁盘位置脱钩」 | 现象完全吻合（内存说 1、磁盘说 6） | `enroll_feat` 恒在 `pos = total` 追加且 `id = total+1`，**槽号 ↔ 位置恒等**（`snap_fail.bin` pos24-28 = id24-28）。脱钩的是 `m_feats` 下标 ↔ 槽号 |
| 「给 esp-dl 打补丁让它返回真实 id」 | 一行改动就能根治，一度已加过 `last_enrolled_id()` | `esp-dl` 在父仓是**无 remote 的 gitlink**，补丁进不了版本库，干净克隆会因缺函数编不过（arena 补丁已是这个状态）。10-27 逐行手工回退，改为板端自算 + 映射 |
| 「名字丢失是 `names_save()` 时机问题」 | 快照 #4 确实有 13 条孤儿 | 只解释了孤儿，主因是 `query_feat(0.999)` 反查到老槽位 |
| 「删除后 900 ms 就导出，导出的是删除前的库（时序竞争）」 | 导出大小和删除前一样 | `delete_feat` 不动 `total`、不缩文件，导出必然是"删除前大小"——这是**格式行为**，900 ms 延时无需改 |
| 「识别率低是阈值/投票/光照」 | 匹配阈值 0.61 看起来偏高 | 遥测显示 `raw 0.917 · 3/3 · stable 1` 全对，唯一错的是查名表那一行 |

## 5. 遗留（已知，不影响验收）

1. `FACE_ENROLL_DEDUP_SIM = 0.95`（`:152`）实测**永不触发** —— 同人跨帧余弦只有 0.92–0.94。应改成"每人限 N 条"（待办 #53/#56），目前靠压实兜底。
2. Qt「从云端同步人脸库到板端」只拉最新版，不支持选历史版本回滚（服务端 `?id=N` 已支持；待办 #57）。
3. **注册后自动同步可能一次都不触发**：自动同步只由 `registered`/`deleted` 这一条 0x02 结果帧触发（`main_window.cpp:1424-1430`），而 `send_result()` 丢弃了 `app_usb_link_send()` 的返回值（`app_faceai.cpp:1255`）—— `cdc_write()` FIFO 满超 500 ms 预算即 `ESP_ERR_TIMEOUT` 静默丢帧，不重发。11:27:43 实测：注册成功、3 s 后签到正常，但日志里既无 `← registered` 也无 `☁ 名单已变化`，云端停在 `#32` 直到手动上传（→ `#33`）。用户明确选择不修，详见 §15.10 遗留 #5；规避：注册后看日志有没有 `☁ 名单已变化`，没有就手动点一次「上传人脸库」。
4. `esp-dl` 的 arena 补丁仍是工作区未入库状态，干净克隆无法直接构建固件（本次修复刻意不再增加对它的依赖）。

## 6. 可复用的排障判据（这次真正救命的几条）

1. **「名字列出来了」不能证明库是好的** —— `lib` 来自内存名表 `s_names[]`，与 `face.db` 是否可用无关（同 [`2026-10-22_storage挂载失败_删除注册失效_修复记录.md`](2026-10-22_storage挂载失败_删除注册失效_修复记录.md)）。
2. **磁盘是唯一权威**：先把 `db_export` 信封解析成 `{槽号→特征}` + 名表，再谈修改；纯靠界面数字（"1 人 / 5 条特征"）会一路被误导。
3. **把看不见的那一行做成遥测再动手**：`raw / 票数 / 窗口 / top1槽` 四元组一次就把问题从"识别算法"缩小到"查名表"，此前所有猜测都在这一步被证伪或证实。
4. **日志面板不能被周期统计冲走**：`imgpipe*` 必须降噪 + 缓冲加到 2000 行，否则现场无法回溯。
5. **不要靠"再注册一次"补救数据正确性 bug** —— 名字绑错人那次就是这么把 `personB` 顶成 `personA` 的，越修越脏。
6. **`esp_err_t` 不是 `bool`**：`ESP_OK == 0`，隐式转 bool 恰好反。
7. **观察运行期不要开 COM3**：打开 COM3 会复位板子并废掉 Qt 的 COM5 句柄，整轮测量静默作废（本次有两次白跑）。
8. **给第三方库打补丁前先问能不能进版本库**：本仓 `esp-dl` 是无 remote 的 gitlink，补丁 = 负债；能在 `jc_p4_app/main` 侧自算就自算。
